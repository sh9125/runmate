# RunMate 작업 인수인계

최종 갱신: 2026-11-09 (Asia/Seoul)

## 0. 새 컨텍스트에서 바로 이어갈 위치 (최신 요약)

이 절이 아래의 과거 미커밋/미검증/다음 행동 기록보다 우선한다.

### 2026-11-09 기존 이벤트 상세 응답에 내 상태 추가 및 자동 검증 완료 (최신)

- 사용자 요청으로 기존 `GET /api/v1/running-events/{eventId}` 응답에 `isCreator`, `applicationStatus`, `endReason`, `waitlistPosition`을 추가했다. 새 API 경로는 만들지 않았다. Controller가 인증 이메일을 서비스에 전달하며, 요청 파라미터의 다른 이메일로 조회 대상을 바꾸지 않는다.
- 미신청은 새 응답 상태 `NONE`, 참가 확정은 `PARTICIPATING`, 유효 대기는 `WAITING`, 취소·종료는 `ENDED`다. 신청 이력이 없는 회원은 개최 취소 이벤트에서도 NONE이다. 순위는 유효 WAITING일 때만 제공한다. 과거 참가 유지 및 정확히 시작 10분 전부터 WAITLIST_CLOSED 처리 정책을 그대로 사용한다.
- 기존 상세의 이벤트 행 비관적 락, 락 획득 후 현재 시각 확인, 시작 시 모집 마감, 상태 변경 시 flush 후 updatedAt 응답 처리를 유지했다. 같은 이벤트 락을 유지한 상태에서 참가·대기 기록과 순위를 읽는다.
- `RunningEventApplicationStateResolver`에 순수 상태 판단 코드를 모아 상세와 마이페이지 종료 사유 처리에 공통 적용했다. 목록 조회 조건·페이징 쿼리는 변경하지 않았다. DTO를 공유하는 생성·수정·개최 취소 응답도 `toCreatorResponse`로 생성자 여부/상태를 채운다. 새 DB 엔티티·컬럼 변경은 없다.
- 검증: `./gradlew.bat test` BUILD SUCCESSFUL(1분 28초), 일반 140개 통과(기존 137 + 상세 웹 3개). `./gradlew.bat concurrencyTest` BUILD SUCCESSFUL(1분 4초), 실제 PostgreSQL 37개 통과(기존 경합 24 + 마이페이지/상세 13). 실패/오류/건너뜀 0. 상세의 생성자·미신청·대기 순위·정원 증가 승급, 10분 전후/정확한 경계, 마지막 취소/개최 취소, 과거 참가, 기존 모집 마감 경합·락 회귀를 확인했다. `git diff --check` 통과.
- 사용자 Swagger 확인은 기존 마이페이지 목록까지 완료됐고, 이번 상세 추가 필드의 실제 Swagger 확인은 아직이다. 서버 재시작 후 기존 테스트 데이터의 생성자/신청자별 상세 응답 중심으로 확인하면 되며 목록 전체 시나리오를 반복하지 않는다.
- 현재 `feature/mypage`, 누적 변경은 미커밋·미푸시다. 상세 구현/자동 검증은 완료됐지만 전체 5단계 완료는 아니다. 다음은 상세 핵심 코드/응답 리뷰·Swagger 확인, 이후 인증 유지 방식·CORS·프론트 스타일 등 남은 범위다.

### 2026-11-09 대기 마감 확인 및 마이페이지 목록 Swagger 검증 종료 (최신)

- 사용자가 SQL UPDATE RETURNING으로 이벤트 10의 start_at을 2026-11-09T00:29:48.272189로 변경한 캡처를 제공했다. 같은 실행의 한국 현재 시각은 00:20:48.277023으로 시작 약 9분 전이다. 앞선 변경 미반영 상태는 이후 정상 갱신됐으며 코드 수정은 하지 않았다.
- 이후 사용자 제공 응답에서 B waiting은 content=[]/totalElements=0, ended에는 이벤트 10이 ENDED/WAITLIST_CLOSED/waitlistPosition=null로 포함됨을 확인했다. 기존 개최 취소 이벤트 9·6도 EVENT_CANCELED로 유지됐다. 이벤트 자체 status=RECRUITING은 대기 마감과 이벤트 모집 마감이 별개이므로 정상이다.
- 마이페이지 목록의 합의한 수동 시나리오(생성자별 목록, 참가·대기·취소/재신청·승급에 따른 목록 이동, 종료 사유, 과거 참가 유지, 대기 시간 마감, 페이징, 비인증 401) 확인을 마무리한다. 세부 캡처의 직접 확인 범위는 아래 기록을 유지하며 AI가 HTTP·DB를 직접 검증한 것으로 표현하지 않는다. 이미 확인한 Swagger 흐름을 다시 요구하지 않는다.
- 이번에는 문서만 갱신했고 자동 테스트를 재실행하지 않았다. 최신 일반 테스트 137개와 직전 PostgreSQL 테스트 31개 통과 기록은 유지한다. 기능/문서는 미커밋·미푸시이며 전체 5단계 완료는 아니다. 다음은 이벤트 상세의 내 참가·대기·생성자 상태 응답 설계/구현, 이후 CORS·프론트 스타일 등 남은 범위를 진행한다.

### 2026-11-09 페이징·비인증 Swagger 확인, 대기 마감 수동 확인 남음 (최신)

- 사용자 제공 JSON 및 Swagger 캡처 6장 검토. 새 이벤트 F는 ID 10, 생성자 ID 2, 정원/현재 인원 1/1, 시작 2026-11-10T20:00:00. B(회원 ID 3)의 대기 등록 201, 대기 순위 1 및 waiting 목록 포함 확인.
- 페이징 수동 확인: A created의 size=1, page=0은 이벤트 10, page=1은 이벤트 9. number/offset은 각각 0/0과 1/1, 두 응답 모두 totalElements=8, totalPages=8, content 1건으로 정상.
- 사용자가 네 목록 비인증 테스트 결과로 제공한 캡처 4장 모두 HTTP 401 및 UNAUTHORIZED 확인. 캡처에 요청 URL은 보이지 않으므로 사용자 시나리오 보고에 따른 네 경로 결과이며 AI가 직접 요청한 것은 아니다.
- 대기 마감 수동 검증은 아직 미확인: 제공한 두 waiting 응답은 모두 이벤트 10의 startAt이 2026-11-10T20:00:00이며 WAITING/순위 1이 유지된다. ended에는 이벤트 9·6만 있고 10은 없다. 미래 시작 시각 기준으로는 정상 응답이며, 이것을 WAITLIST_CLOSED 검증 완료 또는 기능 오류로 판단하지 않는다.
- 다음은 개발 DB의 이벤트 10 start_at을 서버 현재 + 9분으로 조정하고 저장/커밋된 값을 확인한 뒤 B waiting에서 10 제외 및 ended에서 WAITLIST_CLOSED를 확인하는 것뿐이다. 기존 목록 이동·과거 참가·페이징·401은 반복하지 않는다. 스키마/DB 변경이나 HTTP 요청은 AI가 직접 실행하지 않았다. 이번에는 문서만 갱신했고 자동 테스트는 재실행하지 않았다.

### 2026-11-08 사용자 Swagger 시나리오 2~7 응답 확인 (최신)

- 사용자가 제공한 목록 JSON과 Swagger 캡처 8장을 검토했다. AI가 직접 HTTP 요청이나 개발 DB 조회를 실행한 것은 아니다. 테스트 이벤트 E는 ID 9, 시작 2026-11-09T20:00:00, 정원 2. A는 생성자 ID 2, B는 회원 ID 3, C는 회원 ID 5다.
- 2번: A created/participating에 9번 포함(초기 인원 1), B created는 빈 목록. 기존 과거 이벤트 7·4·3·5 등의 CLOSED/PARTICIPATING 응답도 확인되어 과거 참가 내역 유지가 관측됐다.

- 이번에는 검증 기록만 문서에 추가했고 코드·자동 테스트·Git 브랜치/커밋/푸시는 변경하지 않았다. 기존 개발 DB 스키마/데이터 보존을 AI가 직접 검사한 것으로 표현하지 않는다. 전체 5단계 완료는 아니며 상세의 내 상태 정보·CORS·프론트 스타일 등이 남아 있다.

### 2026-11-07 마이페이지 Mapper·Service 구현 및 회귀 검증 (최신)

- `feature/mypage`에서 `MyRunningEventMapper`, `MyRunningEventService` 구현. 내가 만든/참가한/대기 중/취소·종료된 이벤트를 Page로 반환한다. 참가 경로(직접 참가/승급)는 구분하지 않으며 과거 참가도 포함한다. 기본 정렬은 startAt 내림차순, 동률은 id 내림차순이다.
- 대기 순위는 대기 Repository의 `findMyPositions` 인터페이스 projection으로 페이지 내 이벤트를 일괄 조회한다. 종료 사유에 필요한 참가·대기 기록도 각각 일괄 조회한다. 새 서비스는 읽기 전용 REPEATABLE_READ 트랜잭션으로 목록·개수·순위·기록을 같은 DB 스냅샷에서 읽으며, 조회로 이벤트 상태를 변경하지 않는다. 기존 일반 목록/상세의 모집 마감 처리와 구분한다.
- 사용자 추가 합의: 기존 참가·대기 엔티티에 nullable `canceledAt` 추가. 참가 취소 및 대기 취소 시 서버 Clock의 시각을 저장하고 재참가·대기 재신청 시 비운다. 새 엔티티/전체 변경 이력 테이블은 만들지 않는다. 두 취소 기록이 공존하면 더 늦은 취소 시각으로 참가 직접 취소/대기 직접 취소를 구분한다.
- 종료 사유는 개최 취소 우선, 유효하지 않은 WAITING은 대기 마감, 그 외 직접 취소다. 두 취소 기록의 시각이 없어 구분 불가능한 과거 기록(또는 동률)은 새 응답 enum `DIRECT_CANCELED`로 표시하기로 합의했다. 사유가 명확한 기존 기록은 참가/대기 취소로 구분한다. 과거 취소 시각을 추정하여 채우지 않는다.
- 검증: `./gradlew.bat test concurrencyTest` BUILD SUCCESSFUL(2분 1초). 일반 테스트 123개와 실제 PostgreSQL 테스트 31개(기존 경합 24개 + 마이페이지 Repository/Service 7개) 모두 통과. 새 검증에는 페이지별 순위·닉네임, 네 종료 사유·마지막 취소 비교·과거 기록 처리, 재신청 목록 이동과 canceledAt 초기화, 빈 페이지의 전체 개수 유지 및 없는 회원 거절이 포함된다. `git diff --check` 통과. 이 결과를 성능 측정이나 모든 경합 검증 완료로 확대하지 않는다.
- 개발 DB에는 직접 접근하거나 스키마 변경을 실행하지 않았다. local/docker 프로필은 ddl-auto: update이며 다음 애플리케이션 재시작 시 새 canceled_at 컬럼 반영 여부를 확인할 수 있다. 실제 기존 데이터 보존/마이그레이션 검증 및 Swagger는 아직 하지 않았다.
- 현재 DTO·Repository·Mapper·Service·엔티티/테스트·이 문서는 미커밋 상태다. 커밋·푸시 없음. 다음은 새 서비스/매퍼 핵심 리뷰와 Controller 연결이며, 상세의 내 상태·CORS·프론트 스타일 등 5단계 나머지는 미완료다.

#### 확정된 대기 정책과 실제 구현

- 기존 참가 신청 API를 사용한다. 빈자리가 있으면 참가 확정, 만석이고 대기가 열려 있으면 자동 대기 등록. 별도 대기 신청 요청 DTO나 신청 API는 없다. 이벤트 ID는 URL, 회원은 로그인 이메일로 결정한다.
- 선착순은 같은 이벤트 행 락을 잡고 서버가 신청을 접수한 순서다. 사용자와 서버 도착·클릭 순서와 락 획득 순서가 달라질 수 있음을 설명하고 합의했다. 이벤트 행 락을 잡은 트랜잭션 안에서 번호 조회·발급·저장을 처리한다.
- `RunningEventWaitlistEntry` / `running_event_waitlist_entries`를 참가 테이블과 분리한다. 이벤트·회원 유니크 및 이벤트·접수 번호 유니크 제약을 둔다. 상태는 `WAITING`, `CANCELED`. 회원·이벤트당 한 행을 유지하고 취소 후 재신청은 같은 행의 접수 번호·신청 시각을 갱신하여 뒤에 선다. 전체 신청·취소 이력 테이블은 만들지 않는다.
- 접수 번호는 현재 보존된 해당 이벤트 행의 `coalesce(max(queueNumber), 0) + 1`. 현재 순위는 자신보다 접수 번호가 작은 `WAITING` 행 수 + 1이다. 접수 번호와 현재 순위는 다르다. 삭제된 승급 행까지 포함한 영구 증가 번호를 보장하는 카운터는 구현하지 않았다.
- 중복 대기는 `ALREADY_WAITING`으로 거절하고 기존 번호를 유지한다. 현재 참가자는 `ALREADY_PARTICIPATING`. 유효 대기가 없으면 `NOT_WAITING`, 대기 종료 이벤트의 신청·취소·내 순서 조회는 `EVENT_WAITLIST_CLOSED`로 거절한다.
- 대기는 현재 시각 < 시작 시각 - 10분이며 이벤트가 `RECRUITING`일 때만 유효하다. 정확히 10분 전부터 신청·취소·승급과 순위 제공이 종료된다. 그전에는 대기 취소에 추가 마감 제한이 없다. 기존 일반 참가 신청은 빈자리와 모집 상태 조건을 충족하면 시작 전까지 가능하다.
- 참가 취소 → 맨 앞 대기자 한 명 승급은 같은 트랜잭션·이벤트 행 락 안에서 처리한다. 정원 증가도 수정 트랜잭션 안에서 빈자리만큼 접수 번호 오름차순으로 승급한다. 기존 대기자가 신규 신청보다 우선한다. 승급 도중 실패하면 취소나 정원 변경도 롤백된다.
- 승급은 기존 취소된 참가 기록 재활성화 또는 새 참가 기록 생성 및 인원 증가 후 대기 행 삭제. 별도 `PROMOTED` 상태·승급 이력은 두지 않는다. 참가 테이블로 참여 내역을 확인한다.
- **신청 종료 내역 정책**. 직접 대기 취소, 순번 도달 전 대기 마감, 개최 취소를 모두 내 ‘취소·종료된 신청’에서 확인하기로 합의했다. 이유는 구분해 보여준다. 직접 취소 행은 `CANCELED`, 마감·개최 취소로 끝난 대기 행도 삭제하지 않는다. 현재 후자의 저장 상태는 `WAITING`으로 남을 수 있으며 이벤트 상태·시간으로 유효 여부를 판단한다. 스케줄러·일괄 상태 전환은 구현하지 않았다. 내역의 분류·이유 표시·참가/대기 기록 통합 및 중복 처리는 **5단계 구현 대상**이다.

4. 3단계 시작: 현재 참가 수와 실제 PARTICIPATING 기록 수 일치, 정원 초과 없음, 이벤트/회원 중복 없음 등 실험에서 검증할 규칙을 먼저 설명. 실제 PostgreSQL 테스트 환경과 초기 데이터/동시 실행 방법을 준비하고 락 없는 현재 코드로 문제를 먼저 재현·기록
5. 마지막 자리 경쟁·같은 회원 중복 신청부터 시작하고, 참가/개인 취소/재참가/개최 취소/정원 및 날짜 수정/조회 마감 경합으로 확대. DB 유니크 제약의 사후 실패 매핑도 실제 제약별로 검증
6. 원인과 보호 범위를 사용자가 이해한 뒤 조건부 갱신·비관적 락·낙관적 락 등 적합한 후보를 비교·선택·적용. 실제 DB로 정합성과 처리 비용을 재검증. 단위 테스트나 트랜잭션만으로 동시성 해결을 주장하지 않음
7. 학습 방식 유지: AI는 반복 구현/테스트 준비, 사용자는 핵심 설계·결과 예측·측정 해석. 대기열/자동 승급은 동시성 단계 이후. 성능 개선 수치나 특정 기술의 필요성을 미리 단정하지 않음

### 다음 단계에서 결정/검증할 세부 사항

- 확정: 정원 도달 시 RECRUITING 유지, 현재 인원 >= 정원이면 신청 거절. 취소로 빈자리 발생 시 조건 충족하면 신청 가능. 대기열 도입 후에는 대기자 우선 승급
- 확정: 신청/재참가는 RECRUITING이며 현재 < 시작 시각이고 빈자리가 있어야 함. 상세·목록 조회 시 마감 조건을 검사해 DB 상태도 CLOSED로 변경하며, 참가 API는 조회 여부와 무관하게 시간을 직접 검사. 주기적 갱신 및 이벤트별 예약 작업은 현재 범위에서 사용하지 않음
- 확정: 개인 취소는 현재 < 시작 - 10분일 때만 허용. 정확히 10분 전부터 거절. 이 마감 이후 신청한 사람도 취소 불가. 생성자 관리의 15분 규칙은 별개
- 확정: 생성자는 개인 참가 취소 불가, 필요하면 기존 개최 취소 사용
- 확정: 참가 기록은 이벤트/회원당 하나를 유지하고 PARTICIPATING/CANCELED 상태 변경. 재참가 시 같은 기록 재사용. 전체 변경 이력 테이블은 현재 범위 제외
- 확정: 개최 취소 시 이벤트 상태만 변경하고 개인 참가 상태와 인원 보존. 개인 취소와 개최 취소를 두 상태로 구분
- 확정: 미참가/반복 취소는 거절하고 인원 유지. 정상 취소/재참가만 인원 감소/증가
- 엔티티 초안: RunningEventParticipant.cancel/rejoin이 개인 상태와 이벤트 인원을 함께 변경. RunningEvent가 정원·상태·시간·생성자 제한과 모집 종료 규칙 담당. 새 ErrorCode 및 엔티티 테스트 추가
- 신청 서비스: findByRunningEvent_IdAndMember_Id의 Optional 조회로 최초 신청/기존 기록 분기. 최초 신청은 validateParticipationAllowed 후 저장·인원 증가, 기존 기록은 rejoin(now)로 중복 거절 또는 재참가. Clock 주입, 현재 시각 한 번 조회. 재참가 후 서비스에서 인원을 추가 증가시키지 않음
- 개인 취소 서비스: @Transactional에서 회원/이벤트 존재 및 본인의 참가 기록 조회 후 cancel(now) 호출. 미참가 기록은 NOT_PARTICIPATING, 없는 이벤트는 RUNNING_EVENT_NOT_FOUND. 변경 감지로 상태/인원 반영하며 삭제/재저장하지 않음. 웹 테스트는 서비스 Mock이며 실제 DB/JWT 검증과 구분
- 사용자 학습: Optional.get()은 내부 객체 참조를 반환하며 추가 DB 조회/복사 없음. 비어 있으면 null 대신 NoSuchElementException. isEmpty 분기의 return 뒤에는 값 존재가 보장됨
- 기존 DB 참가 행의 새 status 기본값은 @ColumnDefault로 PARTICIPATING 지정. 실제 PostgreSQL 스키마 변경/기존 데이터 보존 검증은 아직 수행하지 않음
- 단순 인원 비교/++/--만으로 동시 요청은 보호되지 않음. 기존 DB 참가 유니크 제약은 서로 다른 회원의 정원 경쟁을 해결하지 않음
- 후속 락 검증에는 참가-참가/참가-개인 취소뿐 아니라 참가-개최 취소, 참가-정원/날짜 수정의 경합도 포함할 것. 현재 관리 API와 참가 API 사이 경합은 아직 보호하지 않음
- 조회 기반 마감도 쓰기 작업이므로 개최 취소·시각/정원 수정·참가와의 경합을 후속 DB 동시성 검증에 포함. 이번 조회 테스트는 Repository Mock이며 실제 커밋/변경 감지/락을 검증한 것은 아님
- DB 유니크 제약에서 뒤늦게 거절된 중복 요청의 오류 매핑은 아직 일반 500. 실제 제약별 분류와 DB 테스트로 보완 예정

## 3. 역할 분담과 학습 방식

- 사용자 합의: 새 작업 브랜치 이름은 항상 feature/로 시작한다. codex/ 접두사 제안을 거절했고 feature/로 명시했다.
- 사용자에게 친구처럼 편하게 반말로 설명한다.
- 사용자는 모든 CRUD를 반복 작성하는 것이 비효율적이라고 판단했고, AI 구현과 핵심 학습을 결합한 방식을 선택했다.
- AI: 일반 CRUD·DTO·Mapper·공통 예외·반복 테스트 준비·테스트 데이터 도구 구현, 프론트 전체 구현과 API 연결.
- 사용자: 업무 규칙 결정, 핵심 코드 리뷰, 결과 예측, 동시성 및 성능 실험 해석, 설계 선택 이유 설명.
- 핵심 로직도 AI가 초안을 작성할 수 있다. 사용자가 전부 직접 타이핑해야 하는 것은 아니다.
- 기존의 '직접 수정 요청 전에는 코드 수정 금지' 방식은 위 역할 분담으로 변경됐다. 다만 이 인수인계 저장만으로 기능 구현까지 시작한 것은 아니다.
- 진행 순서: 짧은 개념 설명 → AI 구현 → 핵심 코드 리뷰 → 사용자 결과 예측 → 테스트/실험 → 사용자 말로 정리.
- 일반 CRUD를 줄마다 설명하지 않는다. 트랜잭션·락·정합성·측정 근거 등 새로운 핵심 개념에 집중한다.
- 이해 여부를 확인할 주제: 트랜잭션만으로 정원 초과를 막지 못하는 이유, 락 대상과 범위, 취소와 승급의 원자성, 병목 판단 근거, 측정 조건의 동일성.
- 기능 마무리 흐름: 전체 테스트 → Swagger 검증 → 커밋 → 푸시 → PR → 병합. 실제 실행은 사용자 지시와 권한 범위에 따라 진행한다. 커밋 메시지는 한국어.
- 노션용 정리를 요청하면 제목과 번호 항목을 사용하고, 일반 개념 뒤에 RunMate 적용 사례를 설명한다.

### 노션 정리글 형식 (사용자 확정)

- 노션 정리글은 사용자가 바로 복사할 수 있도록 채팅 본문에 작성한다. 인수인계 및 작성 예시는 별도로 유지한다.
- 실제 작성 예시: [NOTION-WRITING-EXAMPLE.md](NOTION-WRITING-EXAMPLE.md). 새 컨텍스트에서는 형식 설명만 읽지 말고 이 예시도 확인한다. 사용자가 제시한 Lombok 글의 구조/설명 수준을 보존하고 코드 언어 및 @NonNull 표기 등 사실관계는 보정한 예시다
- 기준 예시는 사용자가 제시한 'Lombok 생성자 어노테이션 정리'. 제목 → 번호가 붙은 항목 → 짧고 쉬운 개념 설명 → 코드 예시/처리 흐름 → 필요한 비교표 → RunMate 적용 예시 → 마지막 한 줄 정리 순서로 작성한다. 주제에 맞게 세부 항목을 구성하되 이 스타일을 유지한다
- 일반 개념을 먼저 설명한 뒤 RunMate의 실제 코드/정책/재현 사례로 연결한다. 동시성 제어를 처음 배우는 수준에 맞춰 어노테이션·메서드·낯선 문법의 역할과 필요한 이유를 설명한다
- 대화 중 사용자가 질문하거나 혼동했던 부분과 바로잡은 설명을 포함한다. 대화에서 부적절하다고 확인한 예시를 정상 사례처럼 재사용하지 않는다. 락 타입 정리에는 LockModeType 종류와 이번 선택 이유도 포함한다
- 긴 내용은 주제별로 독립된 노션 글로 나누고, 각 글마다 제목과 번호를 새로 시작한다. 문단 사이 구분선, 짧은 코드 블록과 비교표를 사용해 복사하기 쉽게 작성한다. 코드 블록 언어는 실제 코드에 맞춰 java/sql/text 등으로 지정한다
- 사용자의 현재 노션 분류는 JAVA, DB, Spring, JPA, 인증과 보안, 성능 개선, 테스트. 정리할 때 어느 분류에 넣을지도 알려준다
- 이번 분류: DB에는 '동시성 문제와 트랜잭션·락', JPA에는 '@Lock과 LockModeType 정리' 및 'RunMate 목록 조회의 락 처리와 변경 감지', JAVA에는 'Map, Stream, map(), var 정리'. 테스트/성능 개선 글은 해당 주제를 실제 학습·측정한 후 별도로 작성한다
- 계획/구현/검증 완료를 구분하고, 로컬 동시성 검증을 성능 개선이나 실제 GitHub CI 성공으로 표현하지 않는다. 성능 수치와 모든 경합에 대한 보장을 만들어 쓰지 않는다
- 2026-11-04 사용자가 예시 문서 보존 후 테스트 환경/Gradle 리뷰 진행을 요청함. 기능 코드 리뷰를 다시 시작하지 말고 테스트 코드 리뷰를 이어간다

## 4. 9단계 목표 계획

하루 5~7시간을 가정한 9일 도전 목표이며 마감 보장은 아니다. 필요하면 2~3일 이상 보완한다. 날짜가 지나도 완료 기준을 충족하지 못하면 완료로 표시하지 않는다. 기능 구현 때문에 성능 검증 단계를 생략하지 않는다.

### 1단계: 정책·공통 예외·이벤트 관리
- Git 상태와 기존 테스트 확인, main 동기화, 작업 브랜치 준비
- 참가/취소/수정/대기 정책 확정
- 오류 응답과 전역 예외 처리
- 이벤트 수정·개최 취소와 테스트
- 완료: 생성자만 수정·취소 가능하고 오류 응답이 일관됨

### 2단계: 정원 제한·참가 취소
- 순차 요청 기준 상태/시간/중복/정원 검사
- 참가 취소·인원 감소·재참가·경계 테스트
