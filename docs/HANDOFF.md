# RunMate 작업 인수인계

최종 갱신: 2026-10-23 (Asia/Seoul)

## 1. 새 대화에서 먼저 읽을 내용

- 이 문서는 사용자와 합의한 최신 목표·범위·작업 방식이다.
- 기존 구현 상세와 환경은 [참가 신청 완료 시점 인수인계](HANDOFF-PARTICIPATION.md)를 참고한다. 목표와 역할 분담이 충돌하면 이 문서를 우선한다.
- 문서의 Git·테스트·실행 환경 정보를 현재 사실로 가정하지 말고 실제 확인한다.
- 작업을 이어갈 때 이 문서를 읽고 현재 진행 위치부터 시작한다. 이미 결정한 범위를 매번 다시 논의하지 않는다.

## 2. 최종 목표와 범위

러닝 이벤트 서비스를 프론트와 연결해 로컬에서 사용할 수 있게 완성하고, 대규모 트래픽을 재현하여 동시성 정확성과 성능 개선을 수치로 검증하는 포트폴리오를 만든다.

필수 범위:
- 기존 회원가입·로그인·내 정보 조회, 이벤트 생성·목록·상세·참가 신청 유지
- 공통 예외 응답·권한 검사·입력 및 업무 규칙 검증
- 이벤트 수정·개최 취소
- 정원 제한·모집 상태 및 시간에 따른 참가 제한·참가 취소·재참가
- 실제 PostgreSQL 기반 동시성 제어와 검증
- 대기 신청·취소·내 순서 조회·자동 승급
- 내가 만든·참여한·대기 중인 이벤트 목록과 페이징
- 화면에 필요한 내 참가 상태·대기 상태·생성자 정보 제공
- 프론트 구현·API 연결·로그인/로그아웃/인증 만료 처리·전체 흐름 검증
- 재현 가능한 테스트 데이터와 k6 시나리오
- 개선 전 측정·병목 분석·성능 개선·동일 조건 재측정·문서화

제외: 내 정보 수정, 비밀번호 변경, 회원 탈퇴, 배포.
보류: 검색 조건 및 검색 기능의 상세 범위, 별도 상태 관리 화면.
추가 범위로 합의되지 않은 것: 추천·채팅·리뷰·외부 알림. 임의로 추가하지 않는다.

별도 관리 화면을 보류해도 참가 가능 상태 검사는 필요하다. 이벤트 수정·개최 취소는 상세 화면에 연결할 수 있다. 수동 모집 마감·완료 전환 기능을 구현 완료로 가정하지 않는다.

## 3. 역할 분담과 학습 방식

- 사용자 합의: 새 작업 브랜치 이름은 항상 feature/로 시작한다. codex/ 접두사 제안을 거절했고 feature/로 명시했다.
- 사용자에게 친구처럼 편하게 반말로 설명한다.
- 사용자는 모든 CRUD를 반복 작성하는 것이 비효율적이라고 판단했고, AI 구현과 핵심 학습을 결합한 방식을 선택했다.
- AI: 일반 CRUD·DTO·Mapper·공통 예외·반복 테스트 준비·테스트 데이터 도구 구현, 프론트 전체 구현과 API 연결.
- 사용자: 업무 규칙 결정, 핵심 코드 리뷰, 결과 예측, 동시성 및 성능 실험 해석, 설계 선택 이유 설명.
- 핵심 로직도 AI가 초안을 작성할 수 있다. 사용자가 전부 직접 타이핑해야 하는 것은 아니다.
- 기존의 '직접 수정 요청 전에는 코드 수정 금지' 방식은 위 역할 분담으로 변경됐다. 다만 이 인수인계 저장만으로 기능 구현까지 시작한 것은 아니다.
- 진행 순서: 짧은 개념 설명 → AI 구현 → 핵심 코드 리뷰 → 사용자 결과 예측 → 테스트/실험 → 사용자 말로 정리.
- 일반 CRUD를 줄마다 설명하지 않는다. 트랜잭션·락·정합성·측정 근거 등 새로운 핵심 개념에 집중한다.
- 이해 여부를 확인할 주제: 트랜잭션만으로 정원 초과를 막지 못하는 이유, 락 대상과 범위, 취소와 승급의 원자성, 병목 판단 근거, 측정 조건의 동일성.
- 기능 마무리 흐름: 전체 테스트 → Swagger 검증 → 커밋 → 푸시 → PR → 병합. 실제 실행은 사용자 지시와 권한 범위에 따라 진행한다. 커밋 메시지는 한국어.
- 노션용 정리를 요청하면 제목과 번호 항목을 사용하고, 일반 개념 뒤에 RunMate 적용 사례를 설명한다.

## 4. 9단계 목표 계획

하루 5~7시간을 가정한 9일 도전 목표이며 마감 보장은 아니다. 필요하면 2~3일 이상 보완한다. 날짜가 지나도 완료 기준을 충족하지 못하면 완료로 표시하지 않는다. 기능 구현 때문에 성능 검증 단계를 생략하지 않는다.

### 1단계: 정책·공통 예외·이벤트 관리
- Git 상태와 기존 테스트 확인, main 동기화, 작업 브랜치 준비
- 참가/취소/수정/대기 정책 확정
- 오류 응답과 전역 예외 처리
- 이벤트 수정·개최 취소와 테스트
- 완료: 생성자만 수정·취소 가능하고 오류 응답이 일관됨

### 2단계: 정원 제한·참가 취소
- 순차 요청 기준 상태/시간/중복/정원 검사
- 참가 취소·인원 감소·재참가·경계 테스트
- 완료: 순차 요청에서 인원과 참가 기록 일치

### 3단계: 동시성 문제 재현·해결
- 실제 PostgreSQL로 동시 참가 문제 재현 및 결과 기록
- 락 방식 비교·선택·적용
- 마지막 자리 경쟁·동일 회원 중복 신청·참가와 취소 경합 검증
- 완료: 정원 초과 없이 현재 인원과 실제 참가 기록 일치

### 4단계: 대기자·자동 승급
- 대기 데이터 구조·순서 기준 설계
- 신청·취소·순서 조회·중복 차단
- 참가 취소와 자동 승급을 하나의 트랜잭션으로 처리
- 순서 추월·중복 승급·동시 취소 검증
- 완료: 순서와 정합성이 동시 요청에서도 유지됨
- 작업이 남으면 5단계의 일반 조회보다 우선 마무리

### 5단계: 마이페이지·백엔드 완성
- 내가 만든/참가한/대기 중인 이벤트 목록, 페이징
- 상세의 내 참가/대기 상태 등 화면용 정보
- CORS·전체 테스트·Swagger 검증
- 프론트 스타일 확인
- 완료: 프론트에 필요한 API 준비

### 6단계: 프론트 구현·연결
- AI가 스타일에 맞춰 공통 레이아웃·회원가입·인증·이벤트 화면·마이페이지 구현
- 참가/취소/대기/수정/개최 취소 API 연결
- 인증 만료·로딩·빈 목록·오류·중복 클릭·기본 반응형 처리
- 사용자가 브라우저에서 피드백
- 완료: 여러 회원으로 생성 → 참가 → 대기 → 취소 → 승급 검증
- 이후 기능 추가 중단, 검증 및 성능 작업에 집중

### 7단계: 부하 재현·기준 측정
- 데이터 생성/초기화 도구, k6 및 관찰 환경 준비
- 조회·인기 이벤트 참가·대기·취소와 승급·혼합 부하 측정
- 점진적으로 부하를 높여 한계와 성능 저하 지점 확인
- 완료: 개선할 병목을 측정 근거로 특정

### 8단계: 병목 개선·재측정
- SQL·실행 계획·쿼리 수·락 대기·트랜잭션·연결 풀·자원 분석
- 가설 수립 → 원인에 맞는 변경 → 동일 조건 측정 → 정합성/부작용 확인
- 캐시 등 기술은 근거가 있을 때 도입
- 효과가 없으면 원인 재검토, 수치를 꾸미지 않음
- 완료: 근거 있는 개선 전후 비교

### 9단계: 추가 검증·결과 정리
- 반복 측정·일정 부하 지속 테스트
- 기능과 동시성 회귀 검증
- 실행/데이터 생성/k6 실험 방법과 문제·원인·해결·전후 수치 문서화
- 사용자가 핵심 설계와 실험 결과 설명
- 완료: 다른 사람이 같은 조건으로 실행·실험 재현 가능

## 5. 아직 결정할 업무 정책

- 수정/개최 취소 시점 및 참가자 존재 시 날짜·장소 제한, 정원 축소, 개최 취소 시 기록 처리는 아래 최신 구현 상태에 확정 정책으로 기록됨
- 생성자의 개별 참가 취소 허용 여부
- 시작 후 참가/취소 가능 여부
- 정원 도달과 CLOSED 상태 관계, 자리 발생 시 재모집 조건
- 개최 취소 시 기존 참가 기록은 보존하기로 확정. 향후 대기 기록 처리의 세부 사항은 대기자 단계에서 결정
- 취소 후 재신청의 기록과 대기 순서 처리
- 대기 순서 기준과 순서 조회 표현
- 검사 순서와 예외 우선순위
- 프론트 디자인과 기술 선택, 인증 유지 방식

관련 단계 시작 시 필요한 정책부터 결정한다. 미결정 사항을 이미 구현된 것으로 서술하지 않는다.

## 6. 성능 포트폴리오의 필수 증거

사용자는 '수치로 나오는 것이 중요하다'고 명시했다. 단순 k6 실행이나 기술 도입만으로 완료 처리하지 않는다.

기록할 항목:
- 평균·p95·p99 응답 시간
- 초당 처리량(RPS), 실패율, 예상된 업무 거절과 시스템 오류 구분
- 요청당 SQL 수·쿼리 실행 시간·실행 계획
- 동시 신청 수·성공/거절 수·정원 초과 및 중복 참가 건수
- 현재 인원과 참가 기록 일치, 중복 승급 및 순서 오류 여부
- 데이터 건수·동시 사용자 수·요청률·실험 시간
- CPU·메모리·DB 연결·락 대기 등 관찰 결과
- CPU/메모리 사양, DB 설정, 부하 발생기 실행 위치와 자원 경합 가능성
- 코드 버전·초기 데이터·설정·부하 조건, 반복 측정의 변동

원칙:
- 기준 측정 → 병목 근거 → 개선 → 동일 조건 재측정
- 목표 숫자를 미리 만들어 맞추거나 가상의 개선 수치를 결과로 쓰지 않음
- 정확성 개선과 처리 성능 개선을 구분하고, 성능 개선 후에도 정합성 재검증
- 실제 운영 경험으로 과장하지 않고 로컬에서 재현한 부하 규모와 장비 한계 명시
- 최종 결과물: 로컬 프론트/백엔드/DB, 자동 테스트, 데이터 생성/초기화 방법, k6 스크립트, 실험 결과, 개선 전후 비교, README
