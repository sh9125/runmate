#### 확정된 대기 정책과 실제 구현

- 기존 참가 신청 API를 사용한다. 빈자리가 있으면 참가 확정, 만석이고 대기가 열려 있으면 자동 대기 등록. 별도 대기 신청 요청 DTO나 신청 API는 없다. 이벤트 ID는 URL, 회원은 로그인 이메일로 결정한다.
- 선착순은 같은 이벤트 행 락을 잡고 서버가 신청을 접수한 순서다. 사용자와 서버 도착·클릭 순서와 락 획득 순서가 달라질 수 있음을 설명하고 합의했다. 이벤트 행 락을 잡은 트랜잭션 안에서 번호 조회·발급·저장을 처리한다.
- `RunningEventWaitlistEntry` / `running_event_waitlist_entries`를 참가 테이블과 분리한다. 이벤트·회원 유니크 및 이벤트·접수 번호 유니크 제약을 둔다. 상태는 `WAITING`, `CANCELED`. 회원·이벤트당 한 행을 유지하고 취소 후 재신청은 같은 행의 접수 번호·신청 시각을 갱신하여 뒤에 선다. 전체 신청·취소 이력 테이블은 만들지 않는다.
- 접수 번호는 현재 보존된 해당 이벤트 행의 `coalesce(max(queueNumber), 0) + 1`. 현재 순위는 자신보다 접수 번호가 작은 `WAITING` 행 수 + 1이다. 접수 번호와 현재 순위는 다르다. 삭제된 승급 행까지 포함한 영구 증가 번호를 보장하는 카운터는 구현하지 않았다.
- 중복 대기는 `ALREADY_WAITING`으로 거절하고 기존 번호를 유지한다. 현재 참가자는 `ALREADY_PARTICIPATING`. 유효 대기가 없으면 `NOT_WAITING`, 대기 종료 이벤트의 신청·취소·내 순서 조회는 `EVENT_WAITLIST_CLOSED`로 거절한다.
- 대기는 현재 시각 < 시작 시각 - 10분이며 이벤트가 `RECRUITING`일 때만 유효하다. 정확히 10분 전부터 신청·취소·승급과 순위 제공이 종료된다. 그전에는 대기 취소에 추가 마감 제한이 없다. 기존 일반 참가 신청은 빈자리와 모집 상태 조건을 충족하면 시작 전까지 가능하다.

- 기준 예시는 사용자가 제시한 'Lombok 생성자 어노테이션 정리'. 제목 → 번호가 붙은 항목 → 짧고 쉬운 개념 설명 → 코드 예시/처리 흐름 → 필요한 비교표 → RunMate 적용 예시 → 마지막 한 줄 정리 순서로 작성한다. 주제에 맞게 세부 항목을 구성하되 이 스타일을 유지한다
