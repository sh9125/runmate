# RunMate 참가·취소 부하 기준 측정

2026-11-12, 기능 코드 기준 `4ea4eaa3f4cb8fb00924a33ffcb51458b82138d3`.

현재 `load-test` 프로필의 기본 모임별 쓰기 진입 한도는 2건이다. 아래 과거 기록에서 모임별 진입 제한 없이 실행한 조건을 재현하려면 API에 `--runmate.load.gate-writes=false`를 명시한다. 1건 조건은 `--runmate.load.gate-writes=true --runmate.load.gate-write-permits=1`을 사용한다.

## 실험 조건

- [조회 실험과 같은 실행 환경](LOAD-TEST-READ.md)에서 Spring `load-test` 프로필과 전용 PostgreSQL 16.14를 사용했다. API, DB, k6 2.3.0은 같은 Windows 호스트의 자원을 공유했다.
- 각 조건 직전에 DB를 초기화했다. 회원 200명, 모임 2개로 구성했다. 모임 1번은 정원 2명에 참가 1명이다. 모임 2번은 정원 91명에 참가 91명이며 90명이 순서대로 대기한다.
- 신청 실험은 모임 1번, 취소·승급 실험은 모임 2번에 요청을 보냈다. 요청마다 다른 회원을 사용하고 회원당 한 번만 요청했다. 첫 신청 한 건은 참가 확정, 이후 정상 신청은 대기 등록이 기대된다. 취소 실험에서는 생성자를 제외한 기존 참가자가 취소하고, DB에서 맨 앞 대기자부터 한 명씩 승급했는지 검증한다.
- 각 실험은 초당 5건 또는 10건으로 8초씩 실행했다. k6 초기 가상 사용자는 30개, 상한은 60개, 응답 제한은 5초였다. 로그인은 요청 전에 실행했고 응답 시간과 실패율 집계에서 제외했다. 별도 예열 없이 각 조건을 한 번씩 측정했다.
- 완료 RPS는 응답이나 오류가 돌아온 요청 수를 8초로 나눈 값이며 구간 종료 직후 돌아온 응답도 포함한다. 응답 시간은 기대한 업무 응답의 평균·p95·p99다. 4xx 거절, 5xx, 시간 초과, 기타 오류, 시작 누락은 별도 집계한다. [k6 오류 코드 문서](https://grafana.com/docs/k6/latest/javascript-api/error-codes/)

## 실행 방법

DB와 API를 띄우고 저장소 루트에서 실행한다. 전용 DB의 실험 데이터가 초기화되므로 각 조건 전에 첫 명령을 실행한다.

```powershell
Get-Content -Raw -LiteralPath load-test/seed.sql |
  docker compose -f load-test/compose.yaml exec -T postgres psql -X -U runmate_load -d runmate_load -v write_baseline=1
docker compose -f load-test/compose.yaml exec -T postgres psql -X -U runmate_load -d runmate_load -c 'ANALYZE;' -c 'SELECT pg_stat_statements_reset();'
k6 run --quiet -e WRITE=apply -e RPS=5 -e SECONDS=8 load-test/write-baseline.js
Get-Content -Raw -LiteralPath load-test/verify-write.sql |
  docker compose -f load-test/compose.yaml exec -T postgres psql -X -q -U runmate_load -d runmate_load --csv
```

`WRITE=cancel`로 취소·승급을, `RPS=10`으로 초당 10건을 실행한다. `RPS × SECONDS`는 초기 데이터의 취소 가능 계정 범위에 맞춰 90보다 작아야 한다.

## 같은 모임에 신청과 취소를 30초간 함께 보낸 실험

2026-11-13. [취소·승급 중간 갱신을 제거한 버전](LOAD-TEST-MIXED.md#8단계-취소승급-중간-인원-저장-제거)에서 신청과 취소가 같은 모임에 계속 들어올 때 응답 시간과 락 대기가 언제 늘어나는지 확인했다.

- 신청자는 아직 신청하지 않은 회원, 취소자는 이미 참가 중인 회원이다. 같은 모임에서 회원마다 한 번만 요청한다. 모임은 만석이고 기존 대기자가 있어 새 신청은 대기열 뒤로 들어가며, 취소 시 첫 대기자가 승급한다.
- 각 조건을 30초간 실행했다. 신청과 취소 각각 초당 5건, 10건, 20건으로 올렸다. 합계 목표는 각각 10, 20, 40 RPS다. 조건 사이에 15초를 뒀고 각 조건은 초기 상태가 같은 별도 모임을 사용했다.
- 세 모임은 각각 정원과 초기 참가자 602명, 기존 대기자 602명으로 준비했다. 회원 1,805명은 한 모임에서 계정을 반복 사용하지 않고 최대 약 600건의 취소와 신청을 각각 보낼 수 있도록 정한 실험용 규모다. 같은 실험 계정은 다음 조건의 다른 모임에 사용할 수 있다.
- 토큰은 기존 로그인 API로 먼저 발급했다. 로그인은 6건씩 나눠 동시에 실행했고 결과의 쓰기 요청 수·시간에서 제외했다. HTTP 시간 제한은 5초다. 쓰기 성공 시간만 평균·p95·p99에 포함하고 시간 초과·HTTP 거절·5xx·시작 누락은 따로 센다.
- 전용 DB에서 20 ms 이상 락 대기 로그를 잠시 켰다. 실제로 락을 얻은 로그를 기준으로 대기 시간과 횟수를 집계하며, 같은 요청에서 여러 번 기록될 수 있다. [PostgreSQL 락 로그 기준](https://www.postgresql.org/docs/16/runtime-config-locks.html)

## 같은 요청에서 DB 연결·락·커밋까지 나눠 잰 실험

2026-11-13. 위 실험에서 약 2초 걸린 요청이 어느 구간에서 시간을 썼는지 확인했다. 만석인 같은 모임에 서로 다른 회원의 신청과 취소를 각각 초당 15건과 20건으로 30초씩 보냈다. 합계 30 RPS와 40 RPS를 비교하며, 초기 상태가 동일한 모임 2번과 3번을 각각 사용했다. 데이터 크기, 요청 제한 시간, 조건 사이의 15초 간격은 앞 실험과 동일하다.

1. **DB 연결 획득**은 쓰기 트랜잭션이 연결 풀에서 연결을 빌리는 데 걸린 시간이다. 인증을 포함해 같은 요청에서 빌린 전체 횟수와 시간도 별도 기록한다.
2. **락을 거는 SELECT**는 모임 행을 잠그는 쿼리를 호출하고 결과를 받을 때까지다. 실제 락 대기 외에 쿼리 실행·결과 반환 시간도 포함한다. PostgreSQL의 개별 20 ms 이상 대기 기록은 DB 연결의 프로세스 ID와 SELECT 시간 범위로 대응시킨다. 이 로그에 잡힌 대기는 SELECT 시간에 이미 포함된다.
3. **락 획득 뒤 커밋**은 SELECT 결과를 받은 뒤 트랜잭션의 커밋 완료까지다. 이 구간에 참가·대기 조회와 갱신, DB 커밋 등이 들어간다.

k6가 보낸 요청 ID를 Spring의 JFR(Java Flight Recorder) 이벤트에도 기록한다. 세 구간 외에 인증 처리, 응답 생성 등에도 시간이 들 수 있어, 전체 HTTP 시간과 세 구간 합에는 차이가 생길 수 있다. 표의 p95는 각 지표를 따로 정렬해서 구하며, 한 요청 안에서 시간을 비교할 때는 CSV의 같은 행을 사용한다.

### 재현 방법

1. 전용 DB에 앞 실험과 같은 `sustained_writes=1` 초기화와 `ANALYZE`를 적용한다. API를 `./gradlew.bat bootRun '--args=--spring.profiles.active=load-test --runmate.load.trace-writes=true'`로 실행한다. 두 설정이 있어야 [계측 코드](../src/main/java/com/runmate/global/config/WriteTraceConfig.java)가 켜진다.
2. 전용 PostgreSQL의 `log_lock_waits`를 `on`, `deadlock_timeout`을 `20ms`로 변경하고 `pg_reload_conf()`를 실행한다. 현재 값을 기록해 두었다가 측정 뒤 복구한다. 측정 시작 시각 이후의 컨테이너 로그를 `build/reports/load-test/request-trace-postgres.log`에 저장한다.
3. JDK의 `jcmd <API PID> JFR.start name=request-trace settings=profile`로 기록을 시작한다. `k6 run --quiet --out json=build/reports/load-test/request-trace-k6.jsonl -e TRACE_WRITES=1 load-test/sustained-writes.js`로 부하를 보내고 표준 출력의 JSON 요약도 저장한다. 응답·DB 작업이 끝나면 `jcmd <API PID> JFR.stop name=request-trace filename=<절대경로>/request-trace.jfr`로 저장한다.
4. `jfr print --json --events com.runmate.WriteRequest build/reports/load-test/request-trace.jfr`의 출력을 `build/reports/load-test/request-trace-jfr.json`에 저장한다. `python load-test/analyze-request-trace.py`는 HTTP·JFR·DB 로그를 연결한 `request-trace-joined.csv`와 집계 결과를 만든다. `verify-sustained-writes.sql`로 인원과 승급·대기 순서를 확인한다.

예를 들어 40 RPS의 신청 `apply_20-213` 한 건은 HTTP 응답에 **4,452 ms**가 걸렸다. 인증 연결에 **2,275 ms**, 쓰기 연결에 **1,925 ms**, 모임 락 SELECT에 **221 ms**, 락을 얻은 뒤 커밋까지 **18 ms**가 걸렸다. SELECT 중 PostgreSQL에 기록된 다섯 번의 대기를 합하면 **199 ms**였다. 이 요청은 DB 연결을 빌리는 데 약 4.2초를 썼다. 30 RPS의 `apply_15-425`는 HTTP 2,295 ms 중 두 차례 연결 998 ms, 락 SELECT 1,145 ms, 커밋까지 129 ms로 락 SELECT가 가장 길었다.

40 RPS에서 가장 크게 늘어난 구간은 연결 획득이다. 모임 행 락을 기다리는 동안에도 그 요청은 연결을 사용 중이어서, 뒤 요청은 연결을 받는 단계부터 밀릴 수 있다. 이 실험으로 확인한 것은 지연이 나타난 위치다. 조건별 한 번의 로컬 실행이며, 앞선 40 RPS의 성공 p95 약 2초와 이번 4.4초 사이에는 차이가 있었다. 계측과 JSON 출력이 성능에 준 영향은 별도로 재지 않았다. JFR 기본 시각·길이는 k6 및 DB 시각과 어긋나 집계에서 제외했다. 구간은 각 계측 값으로 계산하고 DB 로그는 별도로 수집한 SELECT 시작·종료 시각과 맞췄다.

k6와 서버의 요청 2,103건, PostgreSQL 락 대기 기록 6,851개를 연결했다. 40 RPS에서 k6가 5초 내 응답을 받지 못한 523건(43.5%)은 모두 서버에서 커밋까지 마쳤다. HTTP 4xx·5xx와 시작 누락은 0건이었다. DB 검증에서 두 모임 모두 저장·활성 참가 인원 602명, 순서대로 승급 451·601명, 새 대기 등록 451·600명을 확인했다. PostgreSQL 로그 설정은 기본값(`off`, `1s`)으로 복구했다. 일반 자동 테스트 146개가 통과했다. 원시 자료, DB 검증 CSV, 요청별 CSV와 집계는 로컬 `build/reports/load-test/request-trace*`에 있다.

## 같은 모임의 쓰기 요청을 트랜잭션 전에 대기시킨 실험

2026-11-13. 같은 모임의 신청과 취소가 쓰기용 DB 연결을 여러 개 점유하며 락을 기다렸다. 애플리케이션에서 모임별로 쓰기 차례를 기다리면 다른 모임의 조회까지 느려지는 현상이 줄어드는지 실험했다.

- 인증을 마친 참가 신청·취소 요청은 컨트롤러에서 모임 ID별로 차례를 기다린다. 차례가 되면 기존 트랜잭션을 호출하고, 커밋이나 롤백이 끝나서 호출이 반환되면 다음 요청에 차례를 넘긴다. 같은 모임에 대기자와 실행자가 모두 없으면 해당 모임의 대기 상태를 지운다.
- 대기 중인 요청은 쓰기용 DB 연결을 빌리지 않는다. 인증의 DB 조회와 실제 쓰기의 PostgreSQL 행 락은 계속 사용한다. 애플리케이션 대기는 최대 5초이며 초과 시 `503 EVENT_WRITE_BUSY`를 반환한다. 대기에는 HTTP 처리 스레드를 사용한다. 여러 API 인스턴스를 띄우면 모임별 대기는 인스턴스마다 따로 동작한다.
- 같은 코드에서 모임별 대기를 끈 조건과 한 건씩 허용한 조건을 비교했다. 신청과 취소를 각각 20 RPS로 모임 2번에 보내고, 같은 30초 동안 별도 모임 4번의 상세를 3 RPS로 조회한다. 조건별로 DB를 동일한 `sustained_writes=1` 데이터로 초기화하고 `ANALYZE`를 실행한다.
- 두 실행 모두 `--runmate.load.trace-writes=true`와 JFR `settings=default`를 사용한다. PostgreSQL 개별 락 로그는 기본값인 `off`를 사용한다. k6는 로그인 뒤의 측정 구간에서 HTTP 응답 시간과 시간 초과, `EVENT_WRITE_BUSY`, 기타 실패, 시작 누락을 나눠 센다. `gate_wait_ms`는 모임 차례를 기다린 시간이다.

### 재현 방법

앞 절의 초기화·계측·DB 검증 절차를 각 조건에 적용하되, API 실행 시 `--runmate.load.gate-writes=false` 또는 `--runmate.load.gate-writes=true --runmate.load.gate-write-permits=1`을 추가한다. JFR은 `settings=default`로 시작하고 PostgreSQL 설정은 기본값으로 둔다. k6에는 비교 시나리오를 지정한다.

```powershell
k6 run --quiet --out json=build/reports/load-test/request-trace-k6.jsonl -e TRACE_WRITES=1 -e GATE_COMPARISON=1 load-test/sustained-writes.js
```

전후 자료는 별도 디렉터리로 보관한다. 이전 절의 JFR 내보내기 뒤 `python load-test/analyze-request-trace.py <조건별 디렉터리>`를 실행한다. PostgreSQL 락 로그 파일은 비어 있어도 된다. 별도 모임 상세 응답은 k6 JSON 요약의 `detail_3`에서 확인한다.

## 같은 모임의 25·30·35 RPS 중간 구간 측정

2026-11-13. 같은 모임의 쓰기 목표를 합계 25·30·35 RPS로 올리며 별도 모임 상세가 언제 영향을 받는지 확인했다. 각 조건은 30초이고 다음 조건 시작까지 30초를 비웠다. 신청·취소 비율은 1:1이다. k6에서 각 요청 종류에 2초당 25·30·35건을 예약해 초당 12.5·15·17.5건을 균등하게 보냈다. 읽기 부하는 각 구간에 모임 5번 상세 3 RPS를 더했다. 쓰기 대상은 모임 2·3·4번으로 바꿨다. 모임 5번에도 같은 규모의 참가·대기 데이터를 준비했다.

DB 검증에서 부하를 준 모임의 활성 인원과 저장 인원은 모두 602명이었다. 취소·승급은 각각 375·451·526건, 신규 대기는 각각 376·450·526건이고 기존 대기 순서와 일치했다. 조회 모임 5번의 정원·저장 인원·활성 인원·대기 인원은 각각 602명이었다.

조건별 로컬 단일 실행이다. 30 RPS가 25 RPS보다 빨랐고 앞서 동일 모임 쓰기 30 RPS 단일 실행에서는 신청·취소 p95가 약 2.3초였다. 이번 자료로 고정된 처리 한계나 지연이 시작하는 정확한 RPS를 정하기 어렵다. 동일한 모임에 쓰기가 몰리면서 공유 DB 연결에 영향을 주는 상황을 측정했으며, 전체 서비스의 처리량이나 운영 환경의 수용량은 별도 조건에서 확인해야 한다.

## 같은 쓰기 요청량에서 한 모임 집중과 두 모임 분산 비교

2026-11-13. 신청 20 RPS와 취소 20 RPS, 별도 모임 상세 3 RPS를 고정했다. 한 모임에 모두 보내는 조건과 두 모임으로 번갈아 보내는 조건을 비교했다. 분산 조건의 모임당 쓰기는 20 RPS다. 두 조건을 두 번씩 `집중 → 분산 → 분산 → 집중` 순서로 실행했다. 각 쓰기 대상은 초기 상태가 같은 별도 모임이고 각 구간은 30초, 구간 사이는 35초다. 모임 2, 3·4, 5·6, 7이 순서대로 쓰기를 받으며 상세는 항상 모임 8을 조회한다.

앞 절과 같은 전용 DB·API·연결 풀 10개와 5초 HTTP 제한을 사용했다. JFR로 쓰기 요청의 DB 연결 획득 합과 모임 행을 잠그는 SELECT를 재고, 별도 모임 상세의 HTTP 시간은 k6에서 쟀다. PostgreSQL 개별 락 로그는 기본값 `off`로 두고, `pg_stat_activity`를 1초 간격으로 읽어 모임 락 SELECT 중 `Lock`을 기다리는 세션을 세었다. 샘플 최대치는 관측 시점의 수치이며 짧은 대기는 샘플 사이에 지나갈 수 있다.

JFR 기록 및 요청별 CSV 생성은 앞 절과 동일하다. 별도 터미널에서 [락 대기 샘플 SQL](../load-test/sample-event-locks.sql)을 전용 DB에 파이프로 전달한다. 수집이 끝나면 중지한다. 원시 자료는 `build/reports/load-test/final-spread/`에 있다.

### 두 집중 실행에서 대기가 늘기 시작한 시점

앞 실험 원시 자료를 다시 분석했다. 요청 ID로 k6와 JFR을 연결했다. k6의 종료 시각에서 HTTP 소요 시간과 TCP 연결 대기 시간을 빼 클라이언트 요청 시작 시각을 추정했다. 서버 커밋은 락 SELECT 반환의 벽시계 시각에 커밋까지의 경과 시간을 더했다. 초 경계의 집계에는 약간의 오차가 있을 수 있다. 락 SELECT 반환부터 커밋까지의 p95는 그 구간에 락을 얻은 요청 기준이다. [k6 HTTP 메트릭 정의](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/#http-specific-built-in-metrics)

| 각 실행의 시작 후 | 1차 집중 전송 / 커밋 | 2차 집중 전송 / 커밋 | 락 SELECT 이후 커밋까지 p95, 1차 / 2차 |
| --- | ---: | ---: | ---: |
| 0~3초 | 122 / 114건 | 122 / 104건 | 36 / 46 ms |
| 3~6초 | 120 / 82건 | 120 / 136건 | 94 / 29 ms |

두 실행은 시작 후 10초 동안 각각 402건을 보냈다. 첫 10초의 250 ms 단위 전송량은 1차 8~12건, 2차 9~12건이었다. 1차의 3~6초에는 유입 속도가 유지된 상태에서 커밋이 뒤처지기 시작했다. 6~9초에는 락 SELECT 이후 커밋까지의 중앙값이 신청 약 62 ms, 취소 약 109 ms로, 두 요청 종류에서 모두 길어졌다. 같은 시점의 2차 중앙값은 신청 약 16 ms, 취소 약 22 ms였다. 2차는 3~6초에 앞서 쌓인 요청도 처리했다.

1차에서 락을 기다리는 DB 세션은 3~6초에 7→8→9개로 늘었다. 이때부터 도착한 요청들이 DB 연결을 빌리는 데 걸린 시간도 늘어났다. 따라서 비슷한 속도로 들어온 쓰기 요청에 비해 모임 락을 얻은 뒤 처리·커밋하는 속도가 떨어지면서 대기가 누적됐다고 해석한다. 이 기록의 구간에는 업무 처리·SQL·커밋이 함께 포함되므로 내부에서 어느 작업이 처음 느려졌는지는 특정하지 못했다. JFR의 기본 타임스탬프는 벽시계와 차이가 있었으며 표는 별도로 기록한 락 SELECT 반환 시각과 경과 시간을 사용했다. 부하는 추가 실행하지 않았다.

`python load-test/analyze-spread-onset.py`로 `final-spread/onset-stage-*.csv`와 초반 3초 단위 집계를 재생성할 수 있다. CSV의 `sent_minus_committed`는 해당 시점까지 k6에서 시작한 누적 쓰기 건수와 서버 커밋 건수의 차이다. 처리 중인 요청도 포함한다.

## 락을 얻은 뒤 커밋까지의 세부 시간 측정

2026-11-13. 모임 행 락을 얻은 뒤 길어진 시간이 실제 JDBC `commit()` 호출에 있는지 확인했다. 신청 20 RPS와 취소 20 RPS를 같은 모임에 보내고 별도 모임 상세 3 RPS를 더했다. 두 실행 각각 전용 PostgreSQL과 API를 재시작하고 `sustained_writes=1` 초기화, 동일한 계측 점검, `ANALYZE`, k6 로그인, 30초 부하 순서로 진행했다. 로컬 호스트는 두 실행에 공통이며 OS 캐시는 별도로 초기화하지 않았다. 모임별 서버 대기는 끈 상태다.

같은 요청에서 락 SELECT 반환부터 Spring의 `beforeCommit`까지, `beforeCommit`부터 JDBC `Connection.commit()` 호출 직전까지, 실제 `commit()` 호출의 경과 시간을 쟀다. 첫 구간에는 참가·대기 조회 및 신청·취소·승급 처리 중에 실행된 SQL도 들어간다. 두 번째 구간에는 Hibernate가 남은 변경을 반영하는 최종 flush와 커밋 준비가 포함된다. Hibernate의 SQL 실행 시간은 각 구간에 포함된 값으로 별도 기록한다. JDBC 커밋 시간에는 드라이버와 DB 응답까지 포함된다. 세 값의 합과 전체 시간 사이에는 JDBC 반환 후 Spring이 `afterCommit`을 부를 때까지의 짧은 간격이 남는다. [Hibernate 세션 이벤트 정의](https://docs.hibernate.org/orm/7.2/javadocs/org/hibernate/SessionEventListener.html)

기존 `--runmate.load.trace-writes=true`를 켜고, JFR은 `settings=default`로 기록한다. `k6 run --quiet --out json=build/reports/load-test/request-trace-k6.jsonl -e TRACE_WRITES=1 -e GATE_COMPARISON=1 load-test/sustained-writes.js`가 동일한 40 RPS·별도 상세를 재현한다. 앞 절과 같은 방식으로 JFR과 k6를 연결한 뒤 `python load-test/analyze-commit-phases.py <조건별 디렉터리>`로 락을 얻은 시점 기준 3초 단위 지표를 계산한다. 원시 자료는 `build/reports/load-test/commit-run-1/`, `commit-run-2/`에 있다.

계측은 부하 테스트 프로필의 기존 선택 옵션으로만 적용했다. 모임별 대기는 꺼져 있고, 전용 DB에는 2차 데이터가 남았다. 일반 테스트 146개가 통과했다.

## 락을 얻은 뒤 실행한 SQL별 시간과 PostgreSQL 대기

2026-11-13. 커밋 전 SQL의 합계가 길었던 구간을 SQL 문장별로 나눴다. 앞 절과 같은 초기 데이터로 전용 PostgreSQL과 API를 재시작하고, 같은 모임 신청·취소 각 20 RPS와 별도 모임 상세 3 RPS를 30초 보냈다. HTTP가 끝난 뒤에도 요청 수와 DB에 반영된 쓰기 건수를 맞춰 보고 JFR을 닫았다.

`load-test`의 기존 추적 옵션에서 `com.runmate.WriteSql`은 락 SELECT가 반환된 뒤 실행한 JDBC 준비된 문장의 SQL 템플릿, 요청 ID, PostgreSQL 연결 PID, 시작 시각, 실행 경과 시간과 커밋 준비 여부를 기록한다. 바인딩 값은 기록하지 않는다. JDBC 실행 시간에는 DB가 응답할 때까지의 드라이버와 통신 시간도 들어간다. `sample-sql-waits.sql`로 `pg_stat_activity`를 100 ms 간격으로 읽고, 같은 PID·시간 범위에서 실행 중인 쿼리의 대기 상태를 대응시킨다. 짧은 대기는 표본 사이에 지나갈 수 있고, 대기 이벤트가 없는 `active` 상태는 CPU 사용 여부를 확정하지 않는다. [PostgreSQL 활동과 대기 이벤트](https://www.postgresql.org/docs/16/monitoring-stats.html#MONITORING-PG-STAT-ACTIVITY-VIEW)

앞 절과 같이 `TRACE_WRITES=1`, `GATE_COMPARISON=1`, JFR `settings=default`를 사용한다. 첫 준비는 로그인 시간 초과로 중단됐다. 재실행에서는 준비 단계에만 `AUTH_BATCH_SIZE=3`, `AUTH_LOGIN_TIMEOUT=45s`, `AUTH_SETUP_TIMEOUT=8m`을 적용했다. `jfr print --json --events com.runmate.WriteSql` 출력을 `write-sql-jfr.json`, 표본을 `sql-wait-samples.csv`에 저장한다. `python load-test/analyze-write-sql.py`는 `request-trace-joined.csv`의 Hibernate SQL 건수와 JDBC 이벤트 건수를 대조하고 `sql-by-statement.csv`를 생성한다. 원시 자료는 `build/reports/load-test/sql-run-2/`에 있다.

## 같은 모임의 동시 쓰기 진입을 2건·3건으로 제한한 실험

같은 모임의 신청·취소가 쓰기 트랜잭션에 동시에 들어갈 수 있는 수를 2건과 3건으로 바꿔 보고, 제한을 끈 조건과 비교했다. 각 조건은 신청·취소 각각 20 RPS와 별도 모임 상세 3 RPS를 30초 실행했다. 각 조건 전 부하 테스트 전용 PostgreSQL과 API를 재시작하고 동일한 `sustained_writes=1` 데이터를 넣었다. 세 조건은 같은 Windows 호스트를 사용한다. 로그인은 모두 측정 구간 전에 동일한 옵션으로 처리했다.

- 제한 조건은 `--runmate.load.gate-writes=true --runmate.load.gate-write-permits=2` 또는 `3`이다. 쓰기 트랜잭션 전에 같은 모임의 빈 자리를 최대 5초 기다리고, 커밋 또는 롤백이 끝나면 자리를 반환한다. 인증과 PostgreSQL 모임 행 락은 기존대로 적용된다. 입장 시 기록한 `gate_occupancy` 최대치로 실제로 2건 또는 3건이 함께 들어갔는지 확인한다.
- 제한 없는 조건은 `--runmate.load.gate-writes=false`다. 모든 조건에 `--runmate.load.trace-writes=true`와 JFR `settings=default`를 적용했다. PostgreSQL 개별 락 로그는 기본값을 사용했다. k6가 응답을 기다리다 끝난 뒤에도 JFR 쓰기 요청 개수와 k6 쓰기 요청 수를 대조한 다음 기록을 닫았다.


## 대기 등록에서 마지막 접수 번호와 현재 대기 인원을 함께 조회

만석 모임에 신청하면 대기열 맨 뒤에 등록한다. 기존 구현은 마지막 접수 번호를 조회하고 저장한 뒤, 앞에 남은 `WAITING` 행을 다시 세었다. 새 구현은 같은 모임 행 락 안에서 **취소 기록을 포함한 마지막 접수 번호**와 **현재 대기 중인 인원**을 한 SQL로 읽고 등록한다. 등록 전 대기 중인 인원에 1을 더한 값이 신규 신청자의 순위다. 취소 후 재신청도 기존 `CANCELED` 행의 번호를 포함해 새 접수 번호를 구하고, 앞 순위는 `WAITING`만 센다. 나중에 내 대기 순위를 조회하는 경로는 그 시점의 순서를 별도로 계산한다.

대기 등록을 요청하는 초당 20건과 참가 취소·승급 초당 20건을 같은 모임에 보내고, 별도 모임 상세 3 RPS를 함께 보냈다. 변경 전·후 JAR은 모두 모임별 쓰기 진입 한도 2건을 사용한다. 각 조건에 전용 DB·API 재시작과 동일한 `sustained_writes=1` 초기 데이터를 사용했고, 앞 절과 같은 로그인 옵션과 JFR 설정을 적용했다. SQL 횟수는 `com.runmate.WriteSql`로 락 SELECT 반환 뒤 실행한 SQL을 집계했다. 원시 자료는 `build/reports/load-test/queue-before/`, `queue-after/`에 있다.

## 취소 시 다음 승급자와 기존 참가 기록을 한 번에 조회

기존에는 모임 행 락 안에서 맨 앞 `WAITING` 행을 고르고, 그 회원의 해당 모임 참가 기록을 별도 SELECT로 읽었다. 변경 후에는 `LEFT JOIN`으로 두 행을 한 번에 읽는다. `ON`의 `AND`는 같은 모임이고 같은 회원인 참가 기록을 붙이도록 지정한다. `WHERE`는 대기열을 해당 모임의 `WAITING` 행으로 제한한다. 접수 번호 오름차순의 첫 행만 고른다. 참가 기록이 없으면 조인된 값이 `null`이므로 기존대로 새 참가 기록을 저장한다. 정원 증가에 따른 여러 명 승급은 기존 경로를 사용한다.

전후 API에 모임당 쓰기 진입 제한 2건을 적용했다. 같은 만석 모임에 서로 다른 참가자의 취소를 초당 20건씩 30초 보냈다. 초기 대기자 602명은 기존 참가 기록이 없는 회원이다. 매 조건 전 전용 DB·API를 재시작하고 `sustained_writes=1`로 초기화했다. `-e PROMOTION_COMPARISON=1 -e TRACE_WRITES=1`로 `load-test/sustained-writes.js`를 실행한다. 기록과 검증 절차는 직전 실험과 동일하고 원시 자료는 `build/reports/load-test/promotion-before/`와 `promotion-after/`에 있다.

| 항목 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 취소·승급 한 건의 락 이후 SQL | 8회 | 7회 |
| 승급 대상·기존 참가 기록 조회 시간 합 p95 | 30.10 ms | 17.27 ms |
| 락 SELECT 반환부터 커밋까지 p95 | 168.81 ms | 164.38 ms |
| 성공 HTTP 응답 p95 | 4,364 ms | 4,959 ms |
| HTTP 성공 / 시간 초과 / 503 | 224 / 375 / 1 | 249 / 348 / 4 |
| DB 커밋 / 전송 | 445 / 600 | 492 / 601 |

커밋된 모든 요청에서 각각 8회, 7회를 확인했고, 전체 쓰기 1,201건을 JFR과 대응했다. 참가 인원과 승급 순서가 일치했다. 서버의 진입 대기 초과는 각각 155건과 109건이었고, k6가 5초 먼저 시간 초과된 요청은 별도 503 응답으로 집계되지 않았다. 시작 누락·업무 거절·기타 서버 오류는 0건이었다. 일반 테스트 146개와 PostgreSQL 동시성 테스트 47개가 통과했다. 기존 참가 기록이 있는 승급자 복구와 승급 실패 시 롤백은 동시성 테스트에서 확인했다. 8081은 변경 후 버전이다.

취소·승급 단독 부하를 전후 한 번씩 실행한 로컬 결과다. SQL 한 번이 줄고 해당 조회의 p95가 내려갔다. 락 이후 전체 구간 p95의 변화는 작았고, 성공 응답의 p95는 늘었다.

### 신청·취소와 별도 모임 조회를 함께 보낸 전후 비교

승급 조회 변경 직전·직후 JAR을 사용했다. 두 JAR의 애플리케이션 클래스·설정 차이가 승급 조회에 관여하는 서비스와 저장소에 한정된 것을 확인했다. 양쪽에 대기 신청의 번호·순위 통합과 모임별 쓰기 진입 한도 2건이 포함돼 있다. 조건마다 전용 DB와 API를 재시작하고 같은 `sustained_writes=1` 초기 데이터를 넣었다. 같은 모임 신청 20 RPS, 취소 20 RPS, 별도 모임 상세 3 RPS를 30초 보냈다. 순서는 `변경 전 → 변경 후 → 변경 후 → 변경 전`이다. JFR에서 전체 쓰기가 종료된 것을 확인하고 DB 인원·대기·승급 순서도 검증한다.

앞 절의 재현 절차에서 `PROMOTION_COMPARISON=1` 대신 `GATE_COMPARISON=1`을 사용한다. 원시 자료는 `build/reports/load-test/promotion-mixed-*/`에 있다.

| 항목 | 1차 변경 전 → 후 | 2차 변경 전 → 후 |
| --- | ---: | ---: |
| 취소·승급 락 이후 SQL | 8 → 7회 | 8 → 7회 |
| 승급 조회 p95 | 34.99 → 14.86 ms | 31.82 → 13.54 ms |
| 취소·승급 락 이후 커밋 p95 | 155.37 → 145.84 ms | 180.61 → 118.36 ms |
| 신청·취소 DB 커밋 / 전송 | 484/1,200 → 553/1,202 | 392/1,201 → 743/1,200 |
| 신청·취소 HTTP 성공 | 54 → 61건 | 2 → 33건 |
| 신청·취소 시간 초과 | 1,140 → 1,140건 | 1,199 → 1,167건 |
| 별도 모임 상세 p95 | 1,534 → 504 ms | 2,652 → 600 ms |

4회에서 쓰기 4,803건을 JFR과 모두 대응했고, DB 인원·대기·승급 순서 검증을 통과했다. 별도 모임 상세는 매번 전부 성공했다. 클라이언트가 받은 `EVENT_WRITE_BUSY` 503은 순서대로 6·1·0·0건이었다. 기타 오류와 시작 누락은 없었다. 커밋한 쓰기 요청의 모임별 진입 대기 p95는 각 실행에서 약 5초였다. 따라서 조회 구간의 개선과 DB 커밋 증가를 두 비교에서 관찰했으나, 사용자에게 돌아오는 신청·취소 응답은 여전히 대부분 시간 초과였다. 성공 표본이 1건인 시나리오도 있어 성공 요청의 HTTP p95를 전후 개선 판단에 사용하지 않았다. 로컬 30초 비교 두 쌍의 결과다.
