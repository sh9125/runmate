# PostgreSQL 동시성 실험

최신 구현: 이벤트 행의 비관적 쓰기 락 적용. 1~7절은 락 적용 전 실험 기록이며,
현재 소스의 테스트는 결함을 기대하는 테스트에서 정상 규칙을 검증하는 회귀 테스트로 변경됐다.
최신 설계와 실행 결과는 8절을 따른다.

## 1. 목적과 현재 범위

기준 코드: `2c96804`를 포함한 main 병합 커밋 `7f7f8e3`.
락/버전/조건부 갱신을 추가하기 전에 실제 DB에서 결함을 재현한다.
서비스 코드 변경 없이 별도 `concurrencyTest` 소스셋과 Gradle 작업으로 실행한다.
기존 119개 단위/웹 테스트나 완료된 Swagger 검증은 이 작업에서 반복하지 않는다.

## 2. 검증할 규칙

- 현재 인원은 생성자를 포함한 PARTICIPATING 기록 수와 일치해야 한다.
- 실제 참가 인원은 정원 이하여야 한다. 저장된 인원만 정원 이하인 것으로 충분하지 않다.
- 이벤트/회원당 참가 기록은 하나다. 취소 후 재참가는 같은 행을 사용한다.
- 거절된 요청은 인원/개인 상태/이벤트 상태를 변경하지 않는다.
- 개최 취소 자체는 개인 참가 상태와 인원을 보존한다.
- 참가/취소/관리/조회 마감이 겹쳐도 허용된 순차 처리 결과로 설명 가능해야 한다.
  단순히 최종 상태가 CANCELED이고 참가 기록이 있다는 이유만으로 오류라고 판단하지 않는다.
  참가 커밋 후 개최 취소가 실행된 순서라면 기록 보존은 정상이다.
- 정원 도달만으로 CLOSED가 되지 않는다. 참가 시각/개인 취소 10분/관리 15분 규칙은 서로 구분한다.

## 3. 환경과 실행

개발 DB `runmate-postgres:5433/runmate`를 사용하지 않는다.
전용 컨테이너는 볼륨 없이 실행하며 테스트 DB를 Hibernate create-drop으로 초기화한다.

```powershell
docker run --detach --name runmate-concurrency-postgres --publish 127.0.0.1:5434:5432 --env POSTGRES_DB=runmate_concurrency --env POSTGRES_USER=runmate --env POSTGRES_PASSWORD=runmate postgres:16
.\gradlew.bat concurrencyTest
```

컨테이너가 이미 있으면 새로 생성하지 않고 `docker start runmate-concurrency-postgres`로 시작한다.
실험 종료 후 필요하면 `docker stop runmate-concurrency-postgres`로 멈춘다.
테스트가 종료되면 테이블이 제거된다. 테스트 실행 중 이 DB를 다른 용도로 사용하지 않는다.
Context initializer가 Hibernate 초기화 전에 JDBC URL을 검사한다.
데이터 준비 직전에도 DB 이름과 read committed 격리 수준을 확인한다.

실제 확인: PostgreSQL 16.14, Java 17.0.8.1, Spring Boot 4.0.7,
격리 수준 READ COMMITTED, Hikari 최대 연결 4개, 작업 스레드 2개.
호스트 Windows에서 JVM 실행, Docker의 PostgreSQL에 연결한다.
이는 정확성 실험이며 RPS/p95/성능 개선 측정이 아니다.

## 4. 실험 설계

각 테스트는 별도 트랜잭션으로 생성자/두 회원/정원 2명/미래 시작 이벤트/생성자 참가 기록을 커밋한다.
테스트 메서드 전체에 @Transactional을 붙이지 않는다.
두 작업 스레드가 실제 Spring 서비스 프록시를 호출하며 각각 독립된 트랜잭션과 영속성 컨텍스트를 사용한다.
서비스 호출이 커밋까지 성공해야 성공 1건으로 센다. 실패는 숨기지 않고 원인과 제약 이름을 검증한다.

테스트 전용 Repository 프록시는 실제 참가 기록 SELECT가 반환된 직후 CyclicBarrier로 두 작업을 기다린다.
이미 두 요청이 이벤트를 읽고 참가 기록 없음까지 확인한 실행 순서를 의도적으로 만든다.
조회 결과나 저장 결과를 Mock으로 대체하지 않고 실제 INSERT/UPDATE/commit/rollback을 실행한다.
sleep에 의존하지 않으며 barrier/SQL/Future에는 제한 시간이 있다.
완료 후 JDBC로 커밋된 인원과 실제 참가 기록을 새로 읽는다. JPA 캐시 값으로 판정하지 않는다.

| 실험 | 정상적으로 지켜야 할 결과 | 결함 재현 테스트의 기대 관측 |
|---|---|---|
| 순차 대조군 | 첫 회원 성공, 다음 회원 EVENT_CAPACITY_FULL | 저장 인원 2, 실제 인원 2 |
| 서로 다른 두 회원의 마지막 자리 | 최대 1건 성공, 실제 인원 ≤ 2 | 2건 성공, 저장 인원 2, 실제 인원 3 |
| 같은 회원의 동시 최초 신청 | 기록 1개, 두 번째 요청을 업무 오류로 처리 | 1건 성공, 1건 DB 유니크 실패, 저장/실제 인원 2 |

**현재 테스트의 통과는 결함 재현 성공을 뜻한다. 해결 완료를 뜻하지 않는다.**
동일 회원 실험은 `uk_running_event_participant_event_member` 위반을 확인한다.
HTTP를 호출하는 테스트는 아니므로 500 응답을 직접 측정한 것으로 기록하지 않는다.
현재 일반 예외 처리 경로상 이 제약 실패는 업무 오류로 분류되지 않는 문제가 남아 있다.

## 5. 후속 실험과 설계 학습

다음은 참가-개인 취소, 동일 기록의 중복 취소/재참가, 참가-개최 취소,
참가-정원 축소/날짜 변경, 상세/목록의 조회 마감과 관리/참가 경합이다.
각 실행 순서의 허용 결과를 먼저 정하고 측정한다.
이메일/닉네임 등 다른 유니크 제약의 분류도 실제 제약 이름과 DB 테스트로 검증해야 한다.
기존 데이터의 status 기본값 추가 및 보존 마이그레이션 검증은 이번 새 DB 생성 실험으로 대체되지 않는다.

결과를 이해한 뒤 조건부 갱신/비관적 락/낙관적 락을 비교한다.
어느 API가 같은 이벤트를 보호해야 하는지, 참가 기록과 인원 변경을 어디까지 원자적으로 묶는지가 핵심이다.
해결 방식 선택 전부터 특정 기술의 필요성이나 성능 향상을 단정하지 않는다.
락 적용 후에는 두 요청을 조회 뒤에서 기다리는 현재 barrier를 그대로 사용하면 교착 대기가 될 수 있으므로
보호 구간 앞에서 출발을 맞추는 회귀 테스트로 바꾸고 정상 규칙을 assertion으로 검증해야 한다.

## 7. 시작 경계의 참가와 조회 마감 충돌 (2026-11-02 KST)

사용자 지적 반영: 생성자 수정/개최 취소는 시작 15분 전부터,
개인 참가 취소는 시작 10분 전부터 금지된다. 이 제한을 무시한 날짜 수정 예시를
조회 마감 보호의 근거로 삼지 않는다. 이번에는 시작 직전까지 허용되는 참가와
시작 후 상세/목록 마감의 실제 경합만 검증했다.

테스트: `src/concurrencyTest/java/com/runmate/runningevent/RecruitmentClosureRaceTest.java`.

```powershell
.\gradlew.bat concurrencyTest --tests com.runmate.runningevent.RecruitmentClosureRaceTest
```

기존 119개·Swagger·앞선 재현 테스트 3개는 이번에 반복하지 않았다.
운영 코드 및 락 설정은 변경하지 않았다.

### 실행 순서

1. 생성자 1명, 정원 2명, 시작 시각 T의 이벤트와 참가 기록을 별도 트랜잭션으로 커밋한다.
2. 테스트용 Clock을 T-1초로 설정하고 실제 참가 서비스를 호출한다.
3. 참가 조건 통과 후 실제 참가 INSERT가 반환된 지점에서 요청을 대기시킨다.
   참가 트랜잭션은 아직 커밋되지 않았고 이벤트 인원 UPDATE도 실행 전이다.
4. Clock을 T+1초로 변경하고 별도 스레드에서 실제 상세 또는 목록 서비스를 호출한다.
5. 조회가 이벤트의 기존 인원 1/RECRUITING을 읽은 직후 요청을 대기시킨다.
6. 두 요청의 재개 순서를 제어하고 첫 커밋 이후/두 번째 커밋 이후를 JDBC로 확인한다.

Clock만 고정/이동하고 조회 결과·도메인 검사·저장·커밋은 실제 실행한다.
테스트 전용 Repository 프록시와 제한 시간 있는 CountDownLatch로 실행 순서를 만들며 sleep은 없다.
처음 상태를 읽는 시점이 겹치는 상황의 정확성 실험이지 자연 발생 확률 측정이 아니다.
목록은 실제 Pageable 서비스로 호출하며 해당 페이지에 이벤트 1개가 포함됐음을 확인한다.
대규모 페이지/다중 행 락 순서/조회-조회 경합까지 검증한 것은 아니다.

| 조회 | 커밋 순서 | 최종 상태 | 저장 인원 | 실제 활성 기록 | 판정 |
|---|---|---|---:|---:|---|
| 상세 | 마감 → 참가 | RECRUITING | 2 | 2 | 마감 상태 유실 |
| 목록 | 마감 → 참가 | RECRUITING | 2 | 2 | 마감 상태 유실 |
| 상세 | 참가 → 마감 | CLOSED | 1 | 2 | 인원 증가 유실 |
| 목록 | 참가 → 마감 | CLOSED | 1 | 2 | 인원 증가 유실 |
| 상세 | 순차 참가 완료 → 시작 후 조회 | CLOSED | 2 | 2 | 대조군 정상 |
| 목록 | 순차 참가 완료 → 시작 후 조회 | CLOSED | 2 | 2 | 대조군 정상 |

확인한 Hibernate SQL의 핵심 형태:

```sql
update running_events
set capacity=?, creator_id=?, current_participant_count=?, description=?,
    meeting_place=?, preferred_pace_seconds=?, region=?, running_place=?,
    start_at=?, status=?, target_distance_km=?, title=?, updated_at=?

```

현재 매핑에서는 인원만 바꾸거나 상태만 바꾸더라도 UPDATE에 두 컬럼이 모두 포함된다.
참가는 과거 RECRUITING을, 마감은 과거 인원 1을 함께 써서 상대의 커밋을 덮어쓴다.
두 커밋 이후에는 CLOSED/인원 2/활성 기록 2가 보존되어야 하는데 그렇지 않았다.
시작 전 승인된 참가가 시작 후 커밋됐다는 사실 자체를 이번 결함으로 판정한 것은 아니다.

따라서 현재 조회 마감 쓰기도 동시성 해결 범위에 포함해야 한다.
그 해결책이 반드시 페이지 전체 비관적 락이어야 한다는 결론은 아니다.
행 잠금 방식과 상태 조건을 포함한 제한적 UPDATE 등 후보를 보호 범위와 함께 비교할 수 있다.
변경 컬럼만 UPDATE하는 설정만으로 다른 정원 경쟁까지 해결됐다고 주장하지 않는다.

## 8. 이벤트 행의 비관적 쓰기 락 적용

### 합의한 보호 규칙

참가/재참가, 개인 참가 취소, 이벤트 수정/개최 취소, 상세/목록의 조회 마감 모두
이벤트 행을 `PESSIMISTIC_WRITE`로 조회한다. 이벤트 데이터로 판단하기 전에 락을 얻고,
기존 서비스의 @Transactional이 커밋/롤백할 때 DB가 해제한다. 별도의 unlock 호출은 없다.
시간 검사는 락을 얻고 난 뒤 현재 시각을 구해 실행한다.
참가 기록 조회/변경도 이벤트 락 획득 뒤에 하므로 같은 회원의 중복 요청은
앞선 커밋을 확인하고 기존 업무 오류로 거절한다. 유니크 제약도 유지한다.

Repository의 `findByIdForUpdate`가 공통 단일 이벤트 조회 경로다.
실제 Hibernate 7.2.19/PostgreSQL 16 SQL은 `for no key update of re1_0`로 생성됐다.
JPA의 비관적 쓰기 락 요청이 이 환경에서 사용하는 SQL이며,
실제 DB 락 대기와 커밋 후 상태/인원 보존으로 동작을 검증한다.

### 목록 페이지의 보호와 비용

1. 요청한 Pageable로 이벤트 ID 페이지만 조회한다. 이때 엔티티를 먼저 읽지 않는다.
2. 그 ID에 해당하는 이벤트를 ID 오름차순으로 정렬한 쿼리에서 비관적 쓰기 락으로 조회한다.
3. 잠긴 최신 엔티티를 원래 ID 페이지 순서로 재배열한다.
4. 현재 시각을 구하고 조회 페이지의 이벤트에만 마감 규칙을 적용한 뒤 DTO를 만든다.
5. 서비스 커밋 후 락이 해제된다.

응답 정렬과 락 순서를 분리하여 반대 정렬의 페이지 요청도 같은 순서로 락을 얻도록 한다.
빈 페이지에는 락 쿼리가 없다. 페이지 밖 이벤트를 마감하지 않는다.
단일 이벤트 요청은 다른 이벤트의 행 락 때문에 기다릴 필요가 없다.

비용: 기존 목록 조회보다 이벤트 ID 조회 쿼리가 추가되고,
마감 변경이 없는 이벤트도 페이지 트랜잭션 동안 잠근다.
페이지 ID 선택과 엔티티 조회는 두 쿼리이므로 정렬 필드의 동시 수정까지 포함한
목록 전체의 단일 시점 스냅샷을 보장하는 설계는 아니다.
현재 이벤트 삭제 API는 없으며, 두 조회 사이 대상 행이 사라지면 조용히 누락시키지 않고 실패한다.
RPS/응답 시간/락 대기 비용의 성능 측정은 아직 하지 않았다.

### 실제 DB 회귀 테스트의 판정 기준

- 마지막 자리 경쟁: 정확히 1건 성공, 1건 EVENT_CAPACITY_FULL, 저장/활성 인원 2/2.
- 동일 회원 신청: 정확히 1건 성공, 1건 ALREADY_PARTICIPATING. DB 제약 오류가 아님.
- 중복 개인 취소: 정확히 1회 감소, 나머지 NOT_PARTICIPATING.
- 중복 재참가: 정확히 1회 증가, 나머지 ALREADY_PARTICIPATING, 기존 참가 ID 재사용.
- 재참가-신규 참가: 마지막 자리에서 정확히 1건 성공.
- 참가-개인 취소: 취소는 성공, 참가의 선후에 따라 정상 성공 또는 정원 거절. 인원/기록 일치.
- 참가-개최 취소: 개최 취소는 성공, 참가 선후에 따라 기록 보존 또는 EVENT_CANCELED.
- 참가-정원 축소: 한쪽만 성공, 다른 쪽은 정원/현재 인원 규칙으로 거절.
- 참가-날짜 수정: 수정이 먼저면 새 날짜로 참가 가능, 참가가 먼저면 EVENT_DETAILS_LOCKED.
- 상세/목록 마감이 먼저 잠금: 참가가 DB에서 대기하다 CLOSED를 읽고 거절, 저장/활성 1/1.
- 참가가 먼저 잠금: 마감이 DB에서 대기하다 커밋된 인원을 읽고 CLOSED로 변경, 저장/활성 2/2.
- 여러 행의 반대 정렬 목록: 실제 락 대기를 확인하고 두 요청의 정렬/마감 상태 유지.
- 페이지 경계: 정렬/총 개수 유지, 페이지 밖 이벤트는 모집 상태 유지, 빈 페이지 정상 반환.
- 다른 이벤트: 첫 이벤트가 잠겨 있어도 다른 이벤트의 상세 트랜잭션은 완료.

참가/관리 경합은 시작 barrier로 요청을 함께 출발시키고 허용된 순차 결과를 검증한다.
각 가능한 순서를 모두 강제로 재현한 것은 아니다.
상세/목록 마감 경합은 첫 트랜잭션을 멈춘 뒤 `pg_stat_activity.wait_event_type='Lock'`를
확인하고 재개하므로 네 경우 모두 실제 DB 대기가 관측되어야 통과한다.
락 대기 관측은 제한 시간 내 폴링하며, 임의의 sleep 시간으로 실행 순서를 추측하지 않는다.
성공/업무 거절은 실제 서비스의 커밋/롤백까지 확인하고 JDBC로 최종 DB를 읽는다.
현재 테스트는 HTTP/실제 JWT 경로를 실행하지 않는다.

DB 유니크 제약별 전역 오류 매핑, 기존 데이터 마이그레이션 검증,
장시간 부하/다양한 경합 순서의 반복 검증은 여전히 별도 후속 작업이다.
