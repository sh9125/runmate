# RunMate 성능 개선 포트폴리오

## 1. 모집 마감 저장을 분리해 상세 조회의 행 락 경합 해소

**문제.** 같은 러닝 모임의 상세 조회에 30 RPS를 20초간 보내자 성공 응답 p95가 4.51~4.75초까지 늘었다. 5초 안에 응답을 받지 못한 요청과 k6가 가상 사용자 상한에 도달해 시작하지 못한 요청이 모두 발생했다.

**원인 근거.** 상세 조회는 모임 시작 시 모집 상태를 DB에 저장할 수 있도록 `SELECT ... FOR NO KEY UPDATE`로 모임 행을 잠갔다. PostgreSQL에서 락 대기를 관측했고, 30 RPS 재측정에서 잠금 SELECT의 평균 실행 시간은 같은 모임에 집중했을 때 531.587 ms, 모임 100개로 분산했을 때 0.103 ms였다. 부하 종료 후 단일 쿼리는 기본 키 인덱스로 한 행을 찾아 0.098 ms에 실행됐다.

**변경.** 시작 시각이 지난 `RECRUITING` 모임의 상태 저장을 스케줄러의 조건부 UPDATE로 분리했다. 목록·상세는 명시적 행 락을 제거하고 읽기 전용 `REPEATABLE READ`로 전환했다. 상세의 인원과 명단은 같은 DB 스냅샷에서 읽고, 스케줄러 반영 전에도 요청 시각이 시작 시각에 도달하면 모집 마감으로 응답한다. 신청·취소 등 쓰기에는 모임 행 락을 유지했다.

**결과.** 모임 1,000개를 넣은 로컬 전용 DB에서 같은 모임 상세에 목표 30 RPS를 20초씩, 변경 전후 각 두 번 보냈다. 성공 응답 p95는 **4.51~4.75초 → 43.50~45.22 ms**, 전송 요청 실패율은 **16.03~30.64% → 0%**, 시작 누락은 **127~193건 → 0건**이었다. 상세의 요청당 SQL은 7회로 동일했다.

**검증 및 한계.** 실제 PostgreSQL 테스트에서 신청 트랜잭션이 행 락을 보유한 동안 상세가 응답하는지, 모집 마감 작업과 신청이 경합할 때 저장 인원과 참가 기록이 일치하는지 확인했다. 부하 측정 뒤 인원 불일치와 정원 초과는 각각 0건이었다. 수치는 API·DB·k6가 같은 호스트에서 실행된 30 RPS 집중 조회 조건에 해당한다. [원인 근거와 전후 측정](LOAD-TEST-READ.md#30-rps-재측정과-상세-조회-분산-비교)

## 2. 최신 모임 첫 페이지의 목록·개수 SQL을 약 99.3% 절감

**문제와 원인 근거.** 검색·필터 없이 최신 모임 9개를 보는 첫 화면에서 같은 요청이 반복될 때마다 목록 SELECT와 전체 개수 SELECT가 실행됐다. 캐시를 끈 두 측정에서 20초당 600건에 목록과 개수 쿼리가 각각 600회 실행됐다.

**변경.** `createdAt DESC, id DESC`의 첫 9개 응답만 단일 키로 Caffeine에 5초간 저장했다. 캐시가 비어 있을 때 같은 키에 요청이 몰려도 페이지를 한 번만 읽어 채운다. 모임 생성·수정·개최 취소·완료 커밋 뒤 캐시를 비우고, 응답 시 시작 시각을 기준으로 모집 마감 상태를 다시 판단한다. 검색·필터·다음 페이지는 기존 조회 경로를 사용한다.

**결과.** 동일 JAR에서 캐시 설정만 바꿔 첫 페이지에 목표 30 RPS를 20초씩 각 두 번 보냈다. 실행당 목록·개수 SELECT 합계가 **1,200회 → 8회(약 99.3% 감소)**로 줄었고, 성공 응답 p95는 **71.85~182.19 ms → 14.76~30.14 ms**였다. 네 번 모두 실패와 시작 누락이 0건이었다.

**검증 및 한계.** 실제 API에서 생성·수정·개최 취소 직후 첫 페이지 갱신과 검색·다음 페이지를 확인했다. 캐시가 남아 있어도 시작 시각에 모집 마감으로 표시되는 동작을 자동 테스트로 검증했다. 참가 인원과 주최자 닉네임은 만료까지 이전 값이 보일 수 있다. SQL 집계는 인증을 제외한 목록·개수 쿼리 기준이다. 응답 시간은 자동 테스트가 끝난 뒤 같은 호스트에서 다시 측정한 결과이며, 실제 검색·페이지 이동 비율은 실험에 반영하지 않았다. [설계·재현·전후 측정](LOAD-TEST-READ.md#최신-모임-첫-페이지-caffeine-캐시)

## 쓰기 실험에서 확인한 범위

대기 등록의 번호·순위 조회를 통합해 행 락 이후 SQL을 5→4회, 취소·승급의 승급 대상과 기존 참가 기록 조회를 통합해 8→7회로 줄였다. 같은 모임의 신청·취소 합계 40 RPS와 별도 모임 상세 3 RPS를 30초간 보낸 최종 혼합 실험에서는 별도 상세가 모두 성공했고, 쓰기는 5초 HTTP 시간 초과가 계속 발생했다. HTTP 응답과 DB 커밋을 요청별로 대조하고 참가 인원과 대기·승급 순서를 확인했다. 모임당 쓰기 트랜잭션 동시 진입 2건은 `load-test` 프로필에서 적용한 실험 설정이다. [최종 혼합 부하 비교](LOAD-TEST-WRITE.md#신청취소와-별도-모임-조회를-함께-보낸-전후-비교)
