2026-11-12, 기능 코드 기준 `4ea4eaa3f4cb8fb00924a33ffcb51458b82138d3`.

## 재현 조건

- Windows 호스트에서 k6 2.3.0과 Spring Boot 4.0.7, Java 17.0.8.1을 실행했다. CPU는 Intel Core i5-10210U(4코어, 8스레드)다. 같은 호스트의 Docker에서 PostgreSQL 16.14를 실행했다. Docker가 보고한 리소스는 논리 CPU 8개와 메모리 약 7.66 GiB다. API·DB·k6가 호스트 자원을 공유한다.
- Spring `load-test` 프로필, API `127.0.0.1:8081`, DB `127.0.0.1:5435/runmate_load`, Hikari 최대 연결 10개. 회원 100명, 미래에 시작하는 모임 1,000개, 활성 참가 1,001건, 대기 2건이다.
- 목록은 검색 조건 없이 최신순 첫 페이지의 모임 9개, 상세는 모임 1번을 반복 조회했다. 분산 상세는 모집 중인 모임 3~102번을 순환한다. 요청에는 회원 2번의 토큰을 사용했다.
- 목록과 동일 모임 상세를 10 RPS로 5초씩 예열하고 각 조건을 20초씩 측정했다. k6는 초당 지정한 횟수만큼 시나리오 실행을 시작하며, 한 번 실행할 때 GET을 한 건 보낸다. 시작 가상 사용자 40개, 상한 80개, HTTP 제한 시간 5초다.
- 응답 시간은 성공한 조회의 평균·p95·p99다. 완료 RPS는 응답 또는 오류가 돌아온 조회 건수를 예약 구간 20초로 나눈 값이다. 구간 종료 직후에 돌아온 응답도 포함한다. 실패율의 분모는 실제로 전송해 완료한 조회다. 가상 사용자가 부족해 시작하지 못한 횟수는 별도로 기록했다. 준비 단계 로그인은 HTTP 표에서 제외했다.

DB와 API를 시작한 뒤 저장소 루트 PowerShell에서 아래 명령을 실행한다. 초기화 명령은 부하 테스트 전용 DB의 기존 실험 데이터를 지운다.

```powershell
Get-Content -Raw -LiteralPath load-test/seed.sql |
  docker compose -f load-test/compose.yaml exec -T postgres psql -X -U runmate_load -d runmate_load -v read_baseline=1
docker compose -f load-test/compose.yaml exec -T postgres psql -X -U runmate_load -d runmate_load -c 'ANALYZE;'
k6 run --quiet -e READ=list -e RPS=10 -e SECONDS=5 load-test/read-baseline.js
k6 run --quiet -e READ=detail -e RPS=10 -e SECONDS=5 load-test/read-baseline.js
k6 run --quiet -e READ=list -e RPS=10 -e SECONDS=20 load-test/read-baseline.js
```

`READ`는 `list`, `detail`, `detail-spread`를, `RPS`는 실험할 초당 요청 시작 횟수를 받는다. 쿼리 통계는 각 측정 직전에 전용 DB에서 `SELECT pg_stat_statements_reset();`으로 초기화했다. 별도 터미널에서 아래 명령을 실행한 직후 k6를 시작하면 약 23초 동안 250ms 간격의 DB 활동 표본을 얻는다.

```powershell
Get-Content -Raw -LiteralPath load-test/sample-read-activity.sql |
  docker compose -f load-test/compose.yaml exec -T postgres psql -X -U runmate_load -d runmate_load
```

동일 모임 상세 30 RPS 재측정의 실패 125건은 k6 로그의 `request timeout` 125건과 일치했다. k6가 설정한 5초 안에 응답을 받지 못한 건이다. 시작 누락 193건은 가상 사용자 상한에 걸려 HTTP 요청을 보내지 못한 횟수다.

동일 모임 상세 재측정에서 모임 행 잠금 쿼리의 평균 실행 시간은 531.587 ms였다. 같은 쿼리가 100개 모임에 분산됐을 때는 0.103 ms였다. 부하를 종료한 뒤 확인한 단일 쿼리 실행 계획에서는 기본 키 인덱스로 한 행을 찾고 `LockRows`까지 0.098 ms에 끝났다. 첫 측정의 직접적인 락 대기 관측, 재측정의 쿼리 시간, 분산 대조 결과를 함께 보면 동일 모임 행의 락 경합을 우선 조사할 근거가 있다.

목록 30 RPS 재측정에서 9개 행 잠금 쿼리는 평균 153.930 ms, ID 정렬 조회는 0.626 ms, 개수 조회는 0.353 ms였다. 부하를 종료한 뒤 실행 계획을 확인했을 때 ID 조회는 1,000행 순차 스캔과 상위 9개 정렬(0.764 ms), 잠금 조회는 기본 키 인덱스 스캔과 `LockRows`(0.372 ms)였다. 목록은 동일 30 RPS의 p95도 1.08~3.16초로 변동했다.

DB 활동 샘플러는 별도 프로세스에서 시작했다. 재측정에서는 샘플 구간이 부하 구간과 겹쳤는지 확인할 타임스탬프가 없으므로, 재측정의 0건 표본을 락 대기 부재의 근거로 사용하지 않는다. CPU·메모리 사용률과 Hikari 내부 연결 대기 시간은 이번에 기록하지 못했다.

측정 종료 후 모임 1,000개의 저장 참가 인원 합과 활성 참가 기록이 각각 1,001건으로 일치했다. 불일치 0건, 정원 초과 0건, 기존 유효 대기 2건이었다. 원시 HTTP 요약, 쿼리 통계 CSV, 활동 샘플 및 실행 계획은 로컬 `build/reports/load-test/`에 있다.

## 최신 모임 첫 페이지 Caffeine 캐시

프론트의 필터 없는 첫 목록 `GET /api/v1/running-events?page=0&size=9`를 캐시한다. 정렬은 `createdAt DESC, id DESC`이며 키는 하나다. 검색·필터, 다른 페이지 크기, 다른 정렬에는 일반 조회 경로를 사용한다. 결과 DTO와 페이지 정보를 서버 메모리에 5초간 저장한다. 같은 키에 요청이 동시에 들어와도 Caffeine이 캐시를 한 번만 채운다.

API에서 모임 생성·수정·개최 취소·완료 서비스 호출이 성공적으로 커밋된 뒤 캐시를 비운다. 목록의 참가 인원과 주최자 닉네임에는 캐시 만료까지 이전 값이 보일 수 있다. 모집 상태는 캐시를 읽을 때도 모임 시작 시각을 비교해서, 시작된 모임을 모집 마감으로 표시한다. `--runmate.events.latest-cache-enabled=false`로 끌 수 있다.

### 재현

각 조건에 동일한 전용 DB의 모임 1,000개를 사용했다. 동일한 최신순 첫 페이지를 30 RPS로 10초 예열한 뒤 20초 측정을 두 번 실행했다. 각 측정 전에 `pg_stat_statements_reset()`을 호출했다. 목록 조회 SQL과 전체 모임 수를 세는 SQL만 집계했다. HTTP 부하에는 인증 비용도 포함된다.

```powershell
Get-Content -Raw -LiteralPath load-test/seed.sql |
  docker compose -f load-test/compose.yaml exec -T postgres psql -X -U runmate_load -d runmate_load -v read_baseline=1
docker compose -f load-test/compose.yaml exec -T postgres psql -X -U runmate_load -d runmate_load -c 'ANALYZE;'
k6 run --quiet -e READ=list -e RPS=30 -e SECONDS=10 load-test/read-baseline.js
docker compose -f load-test/compose.yaml exec -T postgres psql -X -U runmate_load -d runmate_load -c 'SELECT pg_stat_statements_reset();'
k6 run --quiet -e READ=list -e RPS=30 -e SECONDS=20 load-test/read-baseline.js
```

측정이 끝나면 `pg_stat_statements`에서 `running_events`를 읽는 `SELECT`의 `calls`를 확인한다. 이 부하는 동일 첫 페이지 반복 조회를 가정하며 실제 운영의 검색·페이지 이동 비율은 반영하지 않는다. [Caffeine 로딩 방식](https://github.com/ben-manes/caffeine/wiki/Population)

첫 비교는 캐시 적용 측정과 같은 호스트의 Gradle 자동 테스트 실행이 일부 겹쳤다. 목록 SQL은 요청 601건마다 목록과 개수 각각 601회에서 각각 4회로 줄었다. 응답 시간은 같은 JAR에서 캐시만 끄고 켜 다시 측정해 비교했다.

| 동일 JAR 재측정 | 캐시 끔 1차 | 캐시 끔 2차 | 캐시 켬 1차 | 캐시 켬 2차 |
| --- | ---: | ---: | ---: | ---: |
| 요청 성공 | 600 | 600 | 601 | 601 |
| HTTP p95 | 71.85 ms | 182.19 ms | 30.14 ms | 14.76 ms |
| 목록 SELECT | 600 | 600 | 4 | 4 |
| 전체 개수 SELECT | 600 | 600 | 4 | 4 |

모든 실행에서 실패와 시작 누락은 0건이다. 20초당 목록 SQL 합계는 1,200회에서 8회로 약 99.3% 감소했다. 캐시를 켠 실행마다 601건 중 DB에서 페이지를 다시 읽은 횟수는 4회였다. 캐시 적중률 계측값은 별도로 수집하지 않았다. 인증 SQL은 이 집계에서 제외했다. 응답 속도는 같은 PC의 두 번씩 측정한 결과다. 캐시 활성 API에서 모임 생성·수정·개최 취소 직후 첫 페이지 갱신, 검색과 두 번째 페이지를 확인했다. 캐시가 남아 있어도 시작 시각부터 모집 마감으로 표시되는 동작은 자동 테스트로 확인했다. 일반 147개와 PostgreSQL 47개 테스트가 통과했다. 원시 자료는 `build/reports/load-test/list-cache-control-off/`, `list-cache-control-on/`에 있다.
- 조회 종료 후 저장 인원과 활성 참가 기록은 각각 1,001건, 인원 불일치와 정원 초과는 각각 0건, 대기는 2건이었다.
- 개선 후 원시 요약·SQL·DB 활동은 로컬 `build/reports/load-test/after-list-30-*`와 `after-detail-30-*`에 있다. 활동 샘플은 측정의 일부와 겹치므로 표본에서 대기가 0인 결과는 관찰 구간에 한정한다. 이번 비교는 로컬 30 RPS 조건이다.
