## 실험 조건

- [조회 실험과 같은 실행 환경](LOAD-TEST-READ.md)에서 Spring `load-test`, PostgreSQL 16.14, k6 2.3.0을 사용했다. 실행 프로세스와 DB는 같은 Windows 호스트의 자원을 공유한다.
- 매번 회원 250명과 모임 3개를 초기화했다. 모임 2번은 참가 91명으로 만석이며 대기 90명이다. 모임 3번은 인원·대기·설명이 같은 별도 모임이다.
- 모임 2번에 신청과 참가 취소를 각각 초당 5건씩 보냈다. 회원당 한 번만 신청 또는 취소하며 두 그룹의 계정은 서로 다르다. 신규 신청은 뒤에 대기 등록되고, 취소 때마다 기존 대기 맨 앞에서 한 명이 승급한다.
- 8초씩 한 번 실행한 조건은 조회 없이 신청·취소만 하는 경우, 모임 2번에 상세를 초당 20건 추가한 경우, 모임 3번에 같은 상세 조회량을 보낸 경우다. 상세에는 주최자 계정을 사용했다. 로그인은 측정 전에 실행했다.
- 신청과 취소에 각각 가상 사용자 30개, 상세에는 100개를 미리 할당했다. HTTP 제한 시간은 5초다. 요청 시간은 성공한 업무 응답으로 계산했고, 실패율에는 실제 전송한 요청만 포함한다. 가상 사용자가 부족해 시작하지 못한 횟수는 전체 합계로 따로 기록한다.

## 실행 방법

아래 기준 결과를 재현할 때는 `load-test` API에 `--runmate.load.gate-writes=false`를 명시한다. 현재 프로필의 기본 진입 한도는 모임당 2건이다.

DB와 API를 띄우고 저장소 루트에서 실행한다. 각 조건 전 전용 DB의 실험 데이터를 초기화한다.

```powershell
Get-Content -Raw -LiteralPath load-test/seed.sql |
  docker compose -f load-test/compose.yaml exec -T postgres psql -X -U runmate_load -d runmate_load -v mixed_baseline=1
docker compose -f load-test/compose.yaml exec -T postgres psql -X -U runmate_load -d runmate_load -c 'ANALYZE;' -c 'SELECT pg_stat_statements_reset();'
k6 run --quiet -e READ_TARGET=same load-test/mixed-baseline.js
Get-Content -Raw -LiteralPath load-test/verify-write.sql,load-test/verify-mixed.sql |
  docker compose -f load-test/compose.yaml exec -T postgres psql -X -q -U runmate_load -d runmate_load --csv
```

`READ_TARGET=none`은 상세 조회를 빼고, `READ_TARGET=separate`는 별도 모임 3번을 조회한다. DB 활동은 k6와 나란히 `sample-read-activity.sql`을 실행해 250ms 간격으로 160번 채집했다. 표본 시각을 k6의 로그인 완료 로그와 종료 시각에 대조했다.

## 신청·취소의 DB 연결 대기와 행 락 대기 분리

2026-11-12, 같은 개선 버전에서 조회 없는 조건과 같은 모임 상세를 추가한 조건을 각각 3회 실행했다. 순서는 조회 없음 → 조회 추가 → 조회 추가 → 조회 없음 → 조회 없음 → 조회 추가였다. 매번 혼합 실험 데이터로 초기화했고 신청·취소 각 5 RPS와 실행 시간 8초를 유지했다. 조회 추가 조건은 상세 20 RPS였다.

- **연결 풀 대기**는 JDK Flight Recorder의 `jdk.ThreadPark` 중 호출 경로에 `HikariPool.getConnection`이 있는 1 ms 이상 대기 구간을 셌다. 연결을 얻는 함수 전체의 시간이나 1 ms 미만 대기는 이 값에 포함되지 않는다. JFR 기록은 `jcmd <pid> JFR.start name=<case> settings=none '+jdk.ThreadPark#enabled=true' '+jdk.ThreadPark#threshold=1ms' '+jdk.ThreadPark#stackTrace=true'`로 시작하고 `JFR.stop`으로 저장했다. 호스트 CPU는 `jdk.CPULoad` 1초 표본을 사용했다. [JDK 진단 명령](https://docs.oracle.com/en/java/javase/17/docs/specs/man/jcmd.html)
- **행 락 대기**는 전용 PostgreSQL에서 `log_lock_waits=on`, `deadlock_timeout=20ms`로 임시 설정해 기록했다. 잠금 획득 로그의 실제 대기 시간을 집계했고, 각 로그의 SQL이 `FOR NO KEY UPDATE`인지 확인했다. 한 요청에서 여러 번 기다릴 수 있으므로 횟수는 요청 수와 다를 수 있다. 20 ms 기준 미만 대기는 기록 범위 밖이다. 측정 후 DB 로그 설정을 기본값으로 복구했다. [PostgreSQL 락 로그 기준](https://www.postgresql.org/docs/16/runtime-config-locks.html)
- k6의 로그인 준비 완료 시각부터 실행 종료 시각까지를 집계했다. 원시 k6 요약, JFR, PostgreSQL 로그, DB 검증, 집계 CSV는 로컬 `build/reports/load-test/diagnostic-*`에 있다.

## 신청·취소가 락을 유지하는 구간

2026-11-12, 개선 버전에서 신청·취소 각 5 RPS를 8초씩 보냈다. 상세 조회 없음과 같은 모임에 상세 20 RPS를 추가한 조건을 각각 두 번 실행했다. 매번 전용 DB를 초기화했다. 전용 PostgreSQL에 문장 시간 로그를 잠시 켜고 바인드 값은 기록하지 않았다. 측정이 끝난 후 로그 설정을 기본값으로 복구했다. [PostgreSQL 문장 실행 시간 로그](https://www.postgresql.org/docs/16/runtime-config-logging.html)

같은 PostgreSQL 프로세스의 `SELECT ... FOR NO KEY UPDATE` 완료 로그부터 `COMMIT` 완료 로그까지를 락 유지 시간으로 근사했다. 앞 요청이 락을 풀 때까지 기다린 시간은 잠금 SELECT 자체의 실행 시간에 들어가므로 이 유지 시간에서는 제외된다. 완료 시각의 정밀도는 1 ms다. 아래 DB 시간은 이 구간에서 기록된 Parse·Bind·Execute 및 커밋의 실행 시간을 합한 값이다. 나머지 시간에는 애플리케이션 처리, JDBC 왕복, 스케줄링 등 여러 비용이 섞여 있다. 상세 로깅 자체의 비용도 있으므로 이전 API 기준 측정과 절대값을 직접 비교하지 않는다.

신청 163건과 취소·승급 163건의 커밋을 모두 k6 성공 건수와 대조했다. 실패와 시작 누락은 0건이었다. 네 번 모두 저장·활성 인원 91명, 대기 순서와 승급 수가 맞았다.

- 락을 얻은 뒤 커밋까지 신청은 SQL 6개, 취소·승급은 SQL 10개를 실행했다. 각 실행의 DB 시간 중앙값은 신청 약 3.5~4.8 ms, 취소·승급 약 4.0~5.5 ms였다. 락 유지 시간의 대부분은 여러 SQL을 실행하고 응답을 주고받는 전체 구간에 있었다.
- 취소·승급은 **같은 모임을 두 번 UPDATE**했다. 첫 번째는 기존 참가자 취소를 반영하는 쪽에서, 두 번째는 대기자의 승급 참가를 저장한 뒤 발생했다. 이 실험은 항상 빈자리가 바로 채워져 최종 인원이 91명이 되는 조건이다. 중간의 인원 변경을 한 번만 저장할 수 있는지와, 기존 규칙을 유지하며 락 안의 SQL 왕복을 줄일 수 있는지가 후속 검토 대상이다.
- 원시 로그, k6 요약, DB 검증, 거래별·문장별 집계와 로컬 집계 스크립트는 `build/reports/load-test/lockhold-*` 및 `build/reports/load-test/parse-lockhold.py`에 있다.

## 8단계 취소·승급 중간 인원 저장 제거

2026-11-13. 이전 SQL에서 취소·승급 한 건마다 같은 모임 행을 두 번 갱신했다. 만석 91명에서 A가 취소하고 B가 바로 승급하는 경우, 최종 인원은 91명이다.

### 변경 전 흐름

1. 모임 락을 획득하고 A의 참가 기록을 읽는다.
2. A를 취소로 표시하고 자바 객체의 모임 인원을 90명으로 바꾼다.
3. 대기 1번 B를 찾은 뒤 B의 기존 참가 기록을 읽는다. A의 변경도 같은 참가 테이블에 대기 중이어서 Hibernate의 자동 `flush`가 발생한다. 이때 모임 인원 90명도 같이 DB에 전송된다. 이 단계의 SQL은 같은 트랜잭션 안에 있다.
4. B를 승급해 인원을 91명으로 되돌리고, 모임 행을 다시 갱신한 뒤 커밋한다.

### 변경한 흐름

1. 같은 모임 락 안에서 A가 취소할 수 있는지 확인한다.
2. 대기가 열려 있으면 첫 대기자와 그 사람의 기존 참가 기록을 미리 읽는다.
3. 기존 취소와 승급 동작을 이어서 적용한다. B가 기존에 취소했던 참가자라면 이전 기록을 재활성화하고, 첫 참가라면 기록을 추가한다.
4. 대기자가 없다면 최종 인원 90명을 저장한다. 승급했다면 최종 인원은 91명이고, 참가 명단이 바뀌었다는 기존 `updatedAt` 의미도 보존한다. A의 취소와 B의 승급 기록을 같은 트랜잭션에서 저장한다.

변경 범위는 [참가 취소 서비스](../src/main/java/com/runmate/runningevent/service/RunningEventParticipantService.java)와 [승급 준비·적용 코드](../src/main/java/com/runmate/runningevent/service/RunningEventWaitlistService.java)다. 정원 증가로 여러 명을 승급하는 경로도 같은 승급 동작을 호출한다.

`./gradlew.bat bootJar test concurrencyTest`가 성공했다. 일반 146개와 PostgreSQL 46개 테스트가 통과했다. 기존 동시 취소·승급 및 정원 증가 회귀에 더해, 취소 이력이 있는 대기자가 같은 참가 행으로 복귀하고 모임 수정 시각이 갱신되는지와, 승급 실패 시 취소·인원 감소가 커밋되지 않는지를 검증했다.

### 같은 조건으로 다시 측정한 결과

개선 버전을 8081에 다시 실행하고 혼합 요청으로 한 번 예열했다. 개선 전과 같은 데이터, 신청·취소 각 5 RPS, 상세 조회 추가 시 20 RPS, 8초 실행을 적용했다. 순서도 조회 없음 → 조회 추가 → 조회 추가 → 조회 없음으로 맞췄다. 위와 동일하게 전용 PostgreSQL의 문장 시간 로그를 사용했다. 전후는 각각 별도 실행이며 상세 로그가 켜진 짧은 로컬 실험이다.

| 조건 | 취소·승급 락 중앙값 전 → 후 | 취소·승급 락 p95 전 → 후 | 취소 API p95 전 → 후 |
| --- | ---: | ---: | ---: |
| 조회 없음 1회 | 33 → 39 ms | 47 → 77 ms | 129.21 → 140.93 ms |
| 같은 모임 조회 1회 | 34 → 36 ms | 50 → 114 ms | 81.78 → 154.01 ms |
| 같은 모임 조회 2회 | 32 → 38 ms | 42 → 52 ms | 69.76 → 90.27 ms |
| 조회 없음 2회 | 39 → 40 ms | 73 → 71 ms | 144.47 → 111.20 ms |

- 개선 전후 각각 취소·승급 163건을 실제 커밋 로그와 대조했다. **모임 행 `UPDATE`는 건당 2회에서 1회로 줄었다.** 합계는 326회에서 163회다. 잠금 SELECT가 끝난 뒤 커밋까지 실행한 SQL은 건당 10개에서 9개로 줄었다.
- 락 유지 중앙값은 개선 전 32~39 ms, 개선 후 36~40 ms였다. 이번 실행에서는 락을 잡는 시간이나 API 응답 시간이 줄었다는 근거를 얻지 못했다. SQL 왕복 한 번을 줄인 효과와 로컬 실행 간 편차를 구분할 수 있는 추가 계측은 수행하지 않았다.
- 개선 후 네 실행 모두 실패와 시작 누락이 0건이었다. 모임의 저장·활성 참가 인원 91명, 취소 수와 승급 수, 기존 대기자의 순서 및 새 신청이 대기열 뒤로 들어가는 규칙을 검증했다. 전용 DB의 임시 로그 설정은 기본값으로 되돌렸다.
- 재현은 [혼합 실험 실행 방법](#실행-방법)과 [락 유지 시간 계산법](#신청취소가-락을-유지하는-구간)을 따른다. 원시 결과는 로컬 `build/reports/load-test/lockhold-after-*`에 있고, 전후 거래·문장 집계는 `lockhold-transactions.csv`, `lockhold-steps.csv`에 있다.
