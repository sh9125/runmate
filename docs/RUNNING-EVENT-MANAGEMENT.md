# 이벤트 수정·개최 취소

## 1. 확정 정책

- 생성자만 수정·개최 취소할 수 있다.
- 기존 시작 시각의 15분 전보다 이른 시각에만 허용한다. 19:00 시작이면 18:45:00부터 거절한다.
- 시작 시각을 변경한다면 새 시작 시각도 현재보다 15분 넘게 뒤여야 한다. 기존 마감 검사를 먼저 하므로 날짜를 늦춰 제한을 우회할 수 없다.
- 생성자 외 참가자가 있으면 날짜(시작 시각), 지역, 러닝 장소, 집합 장소를 변경할 수 없다. 같은 값을 제출하는 것은 가능하다.
- 정원은 현재 참가 인원 이상이어야 한다. 참가 인원과 같은 정원은 허용한다.
- 개최 취소는 삭제가 아니라 CANCELED 전환이다. 이벤트·참가 기록·현재 인원을 보존한다.
- 취소/완료된 이벤트는 수정·개최 취소할 수 없다. 취소된 이벤트에는 신규 참가할 수 없다.
- 현재 구현은 RECRUITING/CLOSED를 관리 가능한 상태로 본다. 별도 모집 마감·완료 전환 API는 추가하지 않았다.
- 이 15분 제한은 생성자의 관리 기능 기준이다. 일반 참가자의 신청/취소 마감 규칙은 후속 단계에서 결정한다.

## 2. API

### 수정

```http
PUT /api/v1/running-events/{eventId}
Authorization: Bearer <token>
Content-Type: application/json
```

부분 수정이 아니라 아래 필드를 모두 받는 방식이다. 날짜는 예시이므로 실행 시 적절한 미래 시각으로 바꾼다.

```json
{
  "title": "수정한 러닝 이벤트",
  "description": "수정한 설명",
  "region": "서울",
  "runningPlace": "한강공원",
  "meetingPlace": "여의나루역",
  "startAt": "2030-11-01T19:00:00",
  "preferredPaceSeconds": 360,
  "targetDistanceKm": 5,
  "capacity": 10
}
```

성공: 200과 RunningEventResponseDto. 회원/현재 인원/상태/생성 시각은 수정 요청 필드가 아니다.

### 개최 취소

```http
POST /api/v1/running-events/{eventId}/cancel
Authorization: Bearer <token>
```

본문 없이 호출한다. 성공 시 200과 status=CANCELED인 상세 응답을 반환한다.

## 3. 구현 흐름과 학습 포인트

1. Controller: URL, 로그인 이메일, 수정 DTO를 Service로 전달한다. @Valid로 입력 형식을 검증한다.
2. Service: 이벤트를 조회하고 생성자 이메일과 인증 이메일을 비교한다. 트랜잭션 안에서 처리한다.
3. Entity: 상태·기존 마감·새 시작 시각·참가자 존재 시 변경 항목·정원을 검사한다. 검증을 모두 통과한 뒤 필드를 변경한다.
4. Service: flush로 변경 감지와 Auditing을 반영한 뒤 응답 DTO를 만든다. 다시 save할 필요는 없다. flush 이후에도 트랜잭션은 커밋 전이며 실패 시 롤백할 수 있다.
5. 공통 예외 처리기: 업무 실패를 403/409 및 공통 JSON으로 변환한다.

Clock은 '현재 시각을 제공하는 객체'다. TimeConfig는 서버 기본 시간대의 실제 시계를 제공하고, 테스트에서는 Clock.fixed로 현재 시각을 고정한다. 15분 기다리거나 sleep을 사용하지 않고 마감 직전/정각/직후를 테스트할 수 있다.

JPA Auditing의 updatedAt은 flush 시점에 채워진다. 응답 DTO를 먼저 만들면 예전 updatedAt이 복사될 수 있어 이번 API는 flush 후 변환한다. Clock 주입은 이번 업무 마감 검사에 적용했으며 기존 JPA Auditing의 시간 공급자를 교체하지는 않았다.

## 4. 오류

| 상황 | HTTP | code |
|---|---|---|
| 인증 없음 | 401 | UNAUTHORIZED |
| 없는 이벤트 | 404 | RUNNING_EVENT_NOT_FOUND |
| 다른 회원의 이벤트 관리 | 403 | NOT_EVENT_CREATOR |
| 취소/완료 상태에서 관리 | 409 | EVENT_NOT_MANAGEABLE |
| 기존 시작 시각 기준 마감 도달 | 409 | EVENT_MANAGEMENT_DEADLINE_PASSED |
| 새 시작 시각이 너무 가까움/과거 | 409 | EVENT_START_TOO_SOON |
| 참가자가 있는 이벤트 날짜/장소 변경 | 409 | EVENT_DETAILS_LOCKED |
| 참가 인원보다 작은 정원 | 409 | CAPACITY_BELOW_PARTICIPANTS |
| 취소된 이벤트에 참가 | 409 | EVENT_CANCELED |
| 필수값 누락/형식 검증 실패 | 400 | VALIDATION_FAILED |

업무 검사 순서는 이벤트 조회 → 생성자 권한 → 이벤트 상태 → 기존 마감 → 새 시작 시각(수정) → 날짜/장소 변경 제한 → 정원이다. 여러 조건에 걸리면 먼저 발견한 오류를 반환한다.

## 5. 테스트와 한계

- Service 단위 테스트: 생성자 성공, 타인/없는 이벤트/취소 및 완료 상태 거절, 날짜·장소 변경 제한, 정원 축소, 실패 시 필드 유지
- 고정 Clock: 마감 1나노초 전 성공, 정확한 마감/직후/시작 후 거절, 새 시작 시각의 최소 간격, 기존 마감 우회 방지
- MockMvc: PUT/취소 라우팅, 인증 이메일 전달, 입력 검증, 401/403/409, 응답 상태
- 참가 Service: 취소된 이벤트에서는 참가 저장과 인원 증가가 일어나지 않음
- 이 자동 테스트는 실제 DB 기반 동시성 검증이 아니다. 수정과 참가, 취소와 참가의 경합은 락 도입 단계에서 실제 DB 테스트와 함께 보완한다.

## 6. Swagger 검증 체크리스트와 진행 상태

테스트마다 실패 조건이 섞이지 않도록 충분히 나중에 시작하는 새 이벤트와 생성자 A, 다른 회원 B를 준비한다.

1. A가 생성한 이벤트의 모든 수정 필드를 보내 수정 → 200, 상세 재조회로 변경 및 updatedAt 확인
2. B가 같은 이벤트 수정/개최 취소 → 403
3. B 참가 후 A가 날짜/지역/러닝 장소/집합 장소 중 하나 변경 → 409, 기존 값 유지
4. B 참가 후 날짜/장소를 유지하고 제목·설명·정원 등 수정 → 200
5. 현재 인원보다 작은 정원(현재 2명이라면 1) → 409, 인원과 정원 유지
6. 새 이벤트의 시작 시각을 현재 + 10분으로 수정 → 409
7. 시작이 15분 이내인 별도 이벤트 생성 후 수정/개최 취소 → 409 (생성의 기존 @Future 규칙은 유지)
8. A가 충분히 나중에 시작하는 이벤트 개최 취소 → 200/CANCELED, 상세 재조회 가능, 참가 인원/기록 유지
9. 취소된 이벤트 수정/재취소/참가 → 409, 참가 인원 유지
10. JWT 없이 두 API → 401, 없는 이벤트 → 인증 후 404
11. 필수 필드 누락/빈 제목/정원 0 → 400

정확히 마감 시각을 맞추는 검증은 수동 요청 대신 고정 Clock 자동 테스트 결과를 사용한다. 실제 DB의 변경 반영과 트랜잭션 및 Auditing 동작은 Swagger와 DB 확인으로 보완한다.

### 2026-10-23 사용자 보고 결과

- 확인됨: 가까운 새 시작 시각 거절, 타인 수정/취소 403과 기존 데이터 유지, 참가자 존재 시 시작 시각 변경 거절, 제목/설명 수정 허용, 현재 인원보다 작은 정원 거절/같은 정원 허용 및 상세 조회 일치
- 확인됨: 개최 취소 후 상세 CANCELED 및 DB 참가 기록 보존. 취소 후 수정/재취소/참가 거절과 상태/인원 유지도 안내 후 사용자 완료 보고
- 최초 이벤트는 실제 2026-10-23 18:40 시작이었으며 18:25에 관리 마감. 이후 검증은 2026-10-24 20:00 시작의 새 이벤트, A/B 총 2명으로 진행. 새 정원은 최종 2명
- 지역/러닝 장소/집합 장소 각각의 수동 변경은 반복을 피하려고 생략했고 자동 테스트에서 검증
- 위 결과는 사용자 보고이며 AI가 Swagger 캡처나 DB 조회 결과를 직접 확인한 것은 아님
- 수동 미보고: 기존 시작 기준 마감 후 거절, 새 API의 401/400/404, 실제 updatedAt 갱신. 기존 자동 테스트 결과와 구분할 것
